# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a three-project repo with no shared root tooling — each part is built/run independently:

- `ReviewApp.Api/` — ASP.NET Core 8 Web API (C#), EF Core + SQL Server backend.
- `ReviewApp.Api.Tests/` — the backend test suite (xUnit + Shouldly + NSubstitute): unit, service integration (real SQL Server) and in-process HTTP tests, see "Backend tests" below. A sibling folder because the web SDK project would compile any `.cs` below `ReviewApp.Api/`. It is in `ReviewApp.Api/ReviewApp.Api.sln`, so `dotnet test ReviewApp.Api.sln` from `ReviewApp.Api/` runs it.
- `review-app/` — Preact + TypeScript frontend (built with Vite), using MUI for components and react-router-dom for routing. Its test suite (Vitest) is in `review-app/tests/`, see "Frontend tests" below.
- `review-app-android/` — native Android client (Kotlin, Jetpack Compose + Material 3), being brought up to the web app's feature set milestone by milestone. Mobile wireframes are in `wireframes_mobile/` (gitignored, local only).

## Common commands

### Backend (`ReviewApp.Api/`)

Run all commands from `ReviewApp.Api/`.

```
dotnet run                          # run with default (http) launch profile
dotnet run --launch-profile https   # run with HTTPS (matches frontend CORS origin)
dotnet build
dotnet ef migrations add <Name>     # add a new EF Core migration
dotnet ef database update           # apply migrations to local DB
```

- Swagger UI is served at `/swagger` in Development.
- HTTPS profile listens on `https://localhost:7140` (also `http://localhost:5062`); the frontend's API clients are hardcoded to `https://localhost:7140`, so run the API with the `https` profile when working end-to-end with the frontend. The CORS origin and the links in emails come from `App:FrontendBaseUrl` (`https://localhost:5173` in `appsettings.json`); `Program.cs` refuses to start without it.
- Local connection strings and third-party API keys (TMDb, Spotify) live in `appsettings.Development.json`, which is gitignored (not committed) — each developer creates their own copy locally. The same goes for real SMTP credentials (`Email` section).
- **Subscriptions in development**: the committed `Subscription:Provider` is `Fake` (no payment, no account: "checkout" activates a 30 day subscription at once; only allowed in Development, `Program.cs` refuses to start with it elsewhere). `POST /api/Subscription/dev/simulate` (Development only) plays `PaymentFailed`, `Renewed`, `Ended` or `Lapsed` (period over without a notification, for the expiry job) against the current user's fake subscription. For Stripe test mode set `Subscription:Provider` to `Stripe` and `Stripe:SecretKey`, `Stripe:WebhookSecret`, `Stripe:PriceId` (a monthly EUR price) in `appsettings.Development.json` (the API refuses to start without them), then forward webhooks with the Stripe CLI: `stripe listen --all-snapshot --forward-to https://localhost:7140/api/Subscription/webhook --skip-verify` (newer CLIs require `--all-snapshot` or an `--events` list; event types the API doesn't handle are acknowledged and ignored; its `whsec_...`, also printed by `stripe listen --print-secret`, is the webhook secret), pay with the test card `4242 4242 4242 4242`. Without the CLI the return pages' `sync` still picks the subscription up. The displayed price (`Subscription:PriceAmount`/`Currency`) must match the Stripe price.
- **Emails in development**: the committed `Email` settings point to a local SMTP catcher on `localhost:1025` without auth (e.g. Mailpit, web UI on `http://localhost:8025`). Without one running, sending just fails in the background (logged), the API keeps working. To send real emails, override `Email` (Host, Port, Security = `StartTls`/`SslOnConnect`, Username, Password, FromAddress) in `appsettings.Development.json`.

### Backend tests (`ReviewApp.Api.Tests/`)

Run from `ReviewApp.Api/`. The only prerequisites are the .NET SDK and SQL Server LocalDB (no Docker, no local settings file, no network).

```
dotnet test ReviewApp.Api.sln                                                   # everything
dotnet test ReviewApp.Api.sln --filter "FullyQualifiedName~Tests.Integration"   # one layer: Tests.Unit / Tests.Integration / Tests.Http
dotnet test ReviewApp.Api.sln --filter "FullyQualifiedName~ReviewServiceTests"  # one feature
dotnet test ReviewApp.Api.sln --settings ../ReviewApp.Api.Tests/coverage.runsettings --collect "XPlat Code Coverage"
reportgenerator -reports:../ReviewApp.Api.Tests/TestResults/*/coverage.cobertura.xml -targetdir:../coverage-report   # optional HTML report (dotnet tool install -g dotnet-reportgenerator-globaltool)
```

- **Layers** (folders = namespaces): `Unit/` (pure logic, no database), `Integration/` (the real services from the app's own DI container against a real database, external systems faked), `Http/` (requests through the whole pipeline: auth cookie, rate limits, filters, model binding, status codes). The two older `Subscription*Tests.cs` files in the root are unit tests too. No coverage threshold is enforced.
- **Database**: `Support/TestDatabase` creates one throwaway database per run (`ReviewAppTests_<guid>`, collation pinned to `SQL_Latin1_General_CP1_CI_AS`) through the real migrations, so the triggers, constraints and seeds exist, and drops it on exit (leftovers older than a day are dropped by the next run). LocalDB by default; `REVIEWAPP_TEST_SQL` (a server connection string without database) points to another server, which CI uses. Tests never touch `ReviewAppDb`. They run in parallel in that one database and stay isolated by creating uniquely named data through the `Support/TestData` builders (`TestData.Unique`); never insert the `Favourites` collection (the trigger does), look it up with `FavouritesAsync`. Tests of the expiry and cleanup jobs, which work on every row, are in the non-parallel `GlobalJobsCollection`.
- **Test host**: `Support/ApiFactory` (`WebApplicationFactory<Program>`, so `Program.cs` ends with `public partial class Program`) runs the app in the `Testing` environment, so `appsettings.Development.json` is never loaded and the run is the same as on CI. Settings go in with `UseSetting` (Program.cs reads them eagerly); it uses Stripe with dummy keys only to pass startup validation and replaces `IPaymentProvider` with `TestPaymentProvider` (the Fake provider's behaviour, plus webhooks signed with `TestPaymentProvider.ValidSignature` and per-user outages). TMDb / Spotify are `FakeTmdbService` / `FakeSpotifyService`. The cleanup and expiry hosted services are removed (their work is called directly: `DataCleanupService.CleanupAsync` is internal, `InternalsVisibleTo` the tests); the email dispatcher keeps running and delivers into `CapturingEmailSender` (`App.Mail.WaitForAsync(recipient, subject)`, `LinkToken` / `Code` read the emailed token or 2FA code). `ApiFactory.Shared` is one host for the whole run.
- **HTTP tests**: `As(user)` sends a hand-minted session cookie (`Support/TestTokens`), `Browser()` keeps real cookies for login flows (HTTPS base address, so the `Secure` `__Host-` cookie works). `RateLimiting:PermitMultiplier` (default 1, read in `Program.cs`) is 1000 in the shared host; `RateLimitTests` start their own host with the real limits. `Support/PremiumProbeController` is a test-only `[RequiresFeature]` endpoint, so the paywall tests don't depend on the placeholder `entitlement-preview`.
- **Findings**: `ReviewApp.Api.Tests/FINDINGS.md` lists the bugs the suite found: fixed ones (their tests are regression tests) and open ones, each with a skipped test (`Skip = "Known issue Fx (FINDINGS.md) ..."`) describing the correct behaviour. Un-skip it when fixing the issue.
- **CI**: `.github/workflows/backend-tests.yml` runs the suite on pull requests and pushes to `main` that touch the backend or the tests (or by hand, `workflow_dispatch`), on Ubuntu with a SQL Server service container, no secrets; test results and coverage are uploaded as an artifact.
- **New backend features come with tests**: pure rules as unit tests, the service behaviour as integration tests (happy path, failures, ownership / visibility), and new endpoints in the HTTP smoke tests. A new external system gets a fake in `Support/` and a replacement in `ApiFactory`.

### Frontend (`review-app/`)

Run all commands from `review-app/`.

```
npm start      # vite dev server, https on port 5173, opens browser
npm run build  # production build
npm run preview
npm run typecheck  # tsc --noEmit over src/ and tests/
```

### Frontend tests (`review-app/tests/`)

Run from `review-app/`. The only prerequisite is Node (no backend, no browser, no network).

```
npm test                                   # everything (vitest run)
npm test -- tests/pages/LoginPage.test.tsx # one file; -t "<name>" for one test
npm run test:watch                         # watch mode
npm run test:coverage                      # + coverage (coverage/index.html, cobertura) and test-results/junit.xml
KNOWN_ISSUES=1 npm test                    # runs the known-issue tests as expected failures (see Findings)
npm test -- --sequence.shuffle             # random order, to catch tests that depend on each other
```

- **Stack**: Vitest + jsdom + Testing Library for Preact (`@testing-library/preact`, `user-event`, `jest-dom`) + MSW for the network. Config in `vitest.config.ts`, separate from `vite.config.ts`. `globals: false`, so tests import `describe`/`it`/`expect`/`vi` from `vitest`.
- **Preact as React**: the config aliases `react`/`react-dom`/`react/jsx-runtime` to `preact/compat`, inlines MUI, Emotion, react-router, dnd-kit and react-transition-group (`server.deps.inline`) and resolves their ESM builds (`mainFields` / `conditions`). Real `react` 19 is installed as their peer dependency; any CJS build that `require()`s it brings in a second renderer ("object is not extensible", "Invalid hook call"). `tests/support/environment.test.tsx` guards this, look there first if MUI suddenly fails to render.
- **Layout** mirrors `src/`: `utils/`, `hooks/`, `services/`, `context/`, `components/`, `pages/` with one `Foo.test.tsx` per source file, plus `App.test.tsx` (the route table of `src/App.tsx`). `src/index.tsx` only calls `render(<App />)`; `App.tsx` exports `App`, `AppProviders` (theme, auth, notifications, toasts) and `AppRoutes` (upsell + route table) so tests can mount them under a `MemoryRouter`.
- **Support** (`tests/support/`): `server.ts` (the MSW server, default handlers: anonymous `check-auth`, unseen count 0), `api.ts` (`apiUrl`, `capture(method, path, response)` records what was sent (URL, body, `credentials`, headers), response helpers `ok`/`apiError`/`validationProblem`/`htmlError`/`networkError`/`paymentRequired`, `deferred()` for loading states), `builders.ts` (DTO builders), `handlers.ts` (endpoints many components hit: media stats, replies, collections), `render.tsx` (`renderWithApp(ui, { user, route, path })` = the app's providers + router, `renderApp(route)` = the whole app, `currentLocation()`, `loginAs`, `useFakeTimers`), `browser.ts` (stubs for `location`, `confirm`/`alert`, `matchMedia`, visibility, `muteConsoleError`). `services/endpoint.ts` generates the standard tests of a service method (request, success, `{ error }`, fallback, network failure, non-JSON error).
- **Network rule**: every request needs a handler; one without fails the test after it ends (the services swallow fetch errors, so MSW's own error mode wouldn't). Requests still running at the end of a test are awaited, and after the file the network is closed, so nothing ever reaches `localhost:7140`.
- **Timers**: `useFakeTimers()` fakes timers that still move with real time (findBy / waitFor keep working); `useFakeTimers(undefined, { frozen: true })` + `paint()` / `flush()` for exact timing (debounce). Preact runs effects after the next frame (or 35 ms): advance timers **outside** `act()` when a chain of effects must run (inside `act` it holds every effect until it ends).
- **Locale / time zone**: the app formats with the browser's default locale; the setup pins `en-US` and UTC (`tests/support/locale.ts`) because Node on Windows ignores `LANG`, so results are the same on every machine and CI.
- **jsdom gaps**: no layout (dnd-kit drops are simulated by capturing `onDragEnd`, see `CollectionDetails.reorder.test.tsx`), `scrollIntoView`/`scrollTo` are mocks, `confirm`/`alert`/`location.href` are stubbed per test. MUI Dialogs hide the rest of the page from role queries while open; several selects have no accessible name, query them by the value they show.
- **Findings**: `review-app/tests/FINDINGS.md` lists the bugs the suite found (W1-W19, none fixed by decision), each with skipped tests written with `knownIssue('Wx', ...)` that describe the correct behaviour. Fixing one = turn it into a plain `it`, make it pass, move the finding to "Fixed".
- **CI**: `.github/workflows/frontend-tests.yml` runs on pull requests and pushes to `main` touching `review-app/` (or by hand, `workflow_dispatch`): `npm ci`, type check, tests with coverage, production build; results and coverage are uploaded as the `frontend-test-results` artifact. No secrets. Half the cores are used (`maxWorkers: '50%'`, each jsdom worker is heavy), the full run takes about 3 minutes.
- **New frontend features come with tests**: new service methods through `describeEndpoint`, components and pages with their happy path, failure path, logged-out / not-owner state and loading / empty states, new routes in `App.test.tsx`.

Run all commands from `review-app-android/` (Windows: `gradlew.bat`). Gradle needs a JDK 17+; Android Studio's bundled one works (`JAVA_HOME="C:\Program Files\Android\Android Studio\jbr"`).

Run the API with the `https` profile (it serves both 7140 and 5062).

It needs the second `adb reverse` (5062). Deployed, `MobileReturnBaseUrl` must be the public HTTPS API URL.

That file is per developer and gitignored, so export it once. The PEM export also writes the **private key**, so export outside the project and copy only the `.pem` (anything in `res/raw` is packaged into the APK):

No emulator (`androidTest` only has the template test), no secrets.

## Architecture

### Backend

- **Layering**: `Controllers/` → `Services/` (business logic, interfaces in `Services/Interfaces/`) → `DAL/` (EF Core `AppDbContext` + `Entities/`). Controllers depend on service interfaces, which are registered as scoped in `Program.cs`.
- **Auth**: JWT bearer auth, but the token is normally delivered via an httpOnly cookie (`__Host-jwt_token`, `Secure`, `SameSite=Strict`, `Path=/`) rather than the `Authorization` header — see the `OnMessageReceived` handler in `Program.cs` that pulls the token from the cookie. `UserAuthHelper` (`IUserAuthHelper`) reads the authenticated user's ID from the `"id"` claim; use `GetSecureUserID()` in endpoints that require auth and `GetOptionalUserID()` where auth is optional (e.g. to vary visibility of results for anonymous vs. logged-in users).
  - **Issuing/clearing the cookie**: always go through `ITokenService` (`IssueAuthCookie(user)` / `DeleteAuthCookie()`); it owns the cookie name, cookie options and the 8h lifetime. Don't append/delete the cookie by hand. The token carries only the `id` and `ver` claims (HS256, validated with `ValidAlgorithms` pinned and a 30s `ClockSkew`). `Program.cs` refuses to start if `Jwt:Key` is missing or shorter than 32 bytes.
  - **Revocation (`TokenVersion`)**: `User.TokenVersion` is copied into the `ver` claim; `OnTokenValidated` in `Program.cs` compares it with the DB on every authenticated request and rejects mismatches (missing `ver` = 0). Incrementing `TokenVersion` logs the user out everywhere — this happens on password change (`PUT /api/User/me/password`, which then re-issues a cookie for the current browser), on a confirmed email change and on `POST /api/Auth/logout-all`. Any new "invalidate all sessions" feature should do the same.
  - **Two-factor authentication (email codes)**: when `User.IsTwoFactorEnabled`, `POST /api/Auth/login` (after a correct password only) issues no cookie; it emails a code and returns `{ twoFactorRequired, challengeToken }`. The challenge is a 10 min JWT from `ITokenService.CreateTwoFactorChallenge` with its own audience (`<Jwt:Audience>:2fa-challenge`), so the bearer handler never accepts it as a session, and it carries `ver`, so logout-all / password change kill pending logins. `POST /api/Auth/login/2fa` (challenge + code) issues the cookie, `login/2fa/resend` sends a new code. Enabling requires a verified email; enable/disable are two steps (password -> emailed code) in `SecurityController`. No recovery codes yet (TOTP and recovery codes are planned later).
  - **Security tokens**: `SecurityService` owns email verification, email change and 2FA codes, stored in `SecurityToken` as SHA-256 hashes only (`SecurityTokens` helper: generation, hashing, constant-time compare, lifetimes). Each `SecurityTokenType` is single purpose; issuing a token invalidates older unused ones of the same user + type; consuming is an atomic `ExecuteUpdate`; codes burn after 5 wrong tries; resends have a 60s cooldown. Link tokens (verify 24h, email change 1h) are confirmed by a POST from the frontend page, never by the GET of the link (mail scanners prefetch links).
  - **Email change** (`PUT /api/User/me/email`) needs the password and a verified email; it stores `User.PendingEmail`, mails a confirm link to the new address and a notice to the old one. Confirming sets the email, marks it verified and bumps `TokenVersion` (the browser that confirms keeps a fresh cookie if it's the same user). Existing users start unverified; unverified users aren't restricted except for 2FA and email change.
  - **Login** verifies unknown emails against a dummy BCrypt hash so response time doesn't reveal registered emails. Passwords are capped at 20 characters in DTOs and in `src/utils/validation.ts` — this keeps them under BCrypt's 72-byte limit even with multi-byte characters (C# and JS both count UTF-16 units, each at most 3 UTF-8 bytes), so no separate byte check is needed. Don't raise it above 24 without adding one.
  - **Credentials in transit**: email/password are sent as plain JSON over HTTPS by design (visible in the browser's own DevTools, encrypted on the wire) — don't add client-side hashing/encryption. HSTS (`UseHsts`) is enabled outside Development.
- **Subscriptions (Premium)**: one monthly Premium plan (Stripe, test mode only). `UserSubscription` has one row per user who ever started a checkout (no row = Free, unique `UserID`, cascade with the user; `UpdatedAt` is a concurrency token so two parallel updates can't both notify); `SubscriptionEvent` stores received provider event IDs (dedupe/audit, never payloads). All decisions live in the pure, unit-tested `SubscriptionRules` (entitled while `Active` until the period end + 2 h renewal slack, `PastDue` for a 5 day grace from the first failed payment; `Apply` turns a provider snapshot into stored state; `DetectTransitions` finds Started / PaymentFailed / Cancelled / Ended). The local record only changes from what the provider reports: webhooks (`POST api/Subscription/webhook`, anonymous, signature-verified, not rate limited) are just triggers to fetch the current subscription (`IPaymentProvider.GetSubscriptionAsync`), so they are idempotent and order-independent, and notifications/emails come from local transitions only (`SubscriptionNotifier`, never throws). Providers: `StripePaymentProvider` (Stripe.net; the billing period is on the subscription item; a cancellation is either `cancel_at_period_end` (our cancel endpoint) or a `cancel_at` date (the customer portal), both read by `SubscriptionRules.StripeEndsAtPeriodEnd`) and the Development-only `FakePaymentProvider`, picked by `Subscription:Provider` in `SubscriptionSetup.AddSubscriptions`. `SubscriptionService` endpoints (`api/Subscription`): `plan` (anonymous), `status`, `checkout` / `portal` (return the provider page URL; `platform` web or android decides the return URL), `cancel` (= stop renewing, keep access to the period end) / `resume`, `sync` (asks the provider, used by the return pages), `return/android` (HTML page with the deep link), `dev/simulate`. Checkout, portal, cancel, resume and sync use the `billing` rate limit. `SubscriptionExpiryService` (hosted, every 15 min) re-checks lapsed running subscriptions with the provider and ends them if needed. Cancelling a subscription is not tied to account deletion (which doesn't exist yet) — add that step when deletion is built.
- **Entitlements**: `Entitlements.Catalog` (`Services/Entitlements.cs`) maps stable feature keys (`FeatureKeys`) to the minimum tier; coming-soon features are listed for the plans page but never granted. `IEntitlementService` reads the tier from the DB per request (never from the JWT, so changes apply on the next request). Lock an endpoint with `[Authorize]` + `[RequiresFeature(FeatureKeys.X)]`: users without access get **402** `{ error, code: "premium_required", feature }`, which both clients turn into the upsell. The auth user (`login`, `login/2fa`, `check-auth`) carries `tier`, `isPremium` and `entitlements`; `UserProfileDto.IsPremium` is the public badge. `entitlement-preview` is a placeholder Premium endpoint proving the chain; remove it with the first real Premium feature. A new Premium feature = a key + a catalog entry + `[RequiresFeature]` + the client upsell.
- **Rate limiting**: configured in `Program.cs` (`AddRateLimiter`, `app.UseRateLimiter()` after auth so logged-in users are partitioned by `id`, anonymous ones by IP). A global limit (300/min) applies to every request, plus named policies applied with `[EnableRateLimiting("...")]`: `auth-attempt` (login/register/2FA login step, 10 per 10 min per IP), `credential-change` (change email/password, 2FA enable/disable steps, 5 per 10 min), `email-link` (anonymous verify-email / confirm-email-change, 10 per 10 min per IP, separate so opening links never uses up login attempts), `email-send` (resend verification / login code, 5 per 10 min), `external-api` (`MediaController`, 60/min — protects the TMDb/Spotify quotas), `billing` (subscription actions that call the payment provider, 15 per 10 min per user). Rejections are 429 with a JSON `{ error }` body. Counters are in-memory, so restarting the API resets them.
- **Media model (TPH inheritance)**: `Media` is an abstract EF Core entity with `Movie`, `Series`, and `Music` as concrete subtypes, mapped via table-per-hierarchy using the `MediaType` discriminator (configured in `AppDbContext.OnModelCreating`). Media rows are populated from external APIs — `TmdbService` (movies/series, via `ITmdbService`) and `SpotifyService` (music, via `ISpotifyService`) — and cached locally, keyed by `ExternalApiID` + `MediaType`.
- **Database triggers**: Some invariants are enforced by SQL Server triggers created in migrations rather than in C#: `SetUpdatedAt` on `Review` (auto-updates timestamp) and `AddDefaultCollection` on `User` (creates a default collection on user insert). Keep this in mind when reasoning about `Review`/`Collection` state — it isn't always set from application code.
- **Collections**: `Collection` has a per-user unique `Name` constraint. The default `Favourites` collection (`Collection.DefaultName`, created by the trigger) is permanent: `CollectionService` rejects renaming, editing or deleting it, so its name always identifies it (no other collection can take the name). `CollectionDto.IsDefault` marks it for the frontend. `CollectionMedia` is a join entity with a composite key (`CollectionID`, `MediaID`) and cascade delete from both sides. `GET api/Collection/me/memberships` lists every `{ collectionID, mediaType, externalApiID }` in the caller's collections; the Android app caches it to show favourite/collection state on media cards (the web app doesn't use it yet).
- **Followers**: `UserFollower` is a self-referencing join entity on `User` with a composite key (`FollowerID`, `FollowingID`) and `Restrict` delete behavior (to avoid cascade cycles on `User` deletion).
- **Review replies**: `ReviewReply` (`ReviewReplyService` / `ReviewReplyController`, `api/ReviewReply`) threads are max 3 layers: review -> reply (`ParentReplyID` null) -> reply to reply. The layer is derived from the parent chain (no column); the service rejects replying to a reply that already has a parent. Replies have no visibility of their own — every read/write checks the parent review's visibility (hidden == 404), and private reviews can't be replied to. Deleting a reply is a soft delete (`IsDeleted`, content kept in the DB but never returned); a deleted reply is only listed as a placeholder while it has non-deleted children. Deleting a review cascades to all its replies in the DB (`ParentReply`/`User` FKs are `Restrict`). Listing uses keyset paging (`afterId`) for "load more"; review list responses include a non-deleted `ReplyCount`.
- **Account settings**: `AccountSettingsRoute` (`ui/settings/AccountSettingsScreen`, the web's `AccountSettingsMenu` and its dialogs on one screen) with Account (username, email, password), Security (verification state and resend, the pending email change with cancel, 2FA enable/disable) and Sessions (log out, log out of all devices). Everything goes through `AccountRepository` (`SecurityApi` + the `UserApi`/`AuthApi` account calls). `GET Security/status` is the only source of the email, `pendingEmail` and the 2FA state; the screen reloads it on every resume, and `AccountRepository.status()` also syncs the cached user's `isEmailConfirmed`. The dialog fields and rules (`UsernameForm`, `EmailForm`, `PasswordForm`, `TwoFactorFlow`: password step, then code step, resend re-requests with the kept password) are pure and unit-tested in `ui/settings/AccountForms.kt`. The API doesn't report its 60 s resend cooldown, so the app counts it down itself after a successful send. `logout-all` clears the session locally (`SessionManager.onLoggedOutEverywhere`), and a confirmed email change (on the web) revokes the app's session, which then logs out on its next request. The `credential-change` rate limit (5 per 10 min) is easy to hit while testing; restarting the API resets it.
- **Email verification**: the email links point to the web frontend and stay there (no Android link handling). `EmailVerificationBanner` (`VerificationBannerViewModel`) shows on Home and the owner's profile while the user is unverified, with "Resend email" and a dismiss that lasts until the app restarts (`AccountRepository.verificationBannerDismissed`, in memory). While it is shown, every resume calls `SessionManager.refreshUser()` (`check-auth`), so verifying in the browser hides it.
- **Achievements**: `Achievement` holds one row per tier (bronze/silver/gold); the tiers of one card share a `GroupCode` and a `Metric` (`AchievementMetric`, what is counted). `Categories` is a `[Flags]` enum (`AchievementCategories`), so one achievement can be in several categories. Definitions are seeded with `HasData` from `DAL/AchievementSeed.cs` — keep the IDs stable and add new tiers with new IDs plus a migration. `UserAchievement` (cascade deleted with the user) stores `CurrentProgress` and `IsUnlocked`; a missing row means zero progress.
  - **Evaluation**: `AchievementService.EvaluateAsync(userId, metrics...)` recounts the real totals and is called after `SaveChangesAsync` when content is created (and when a review is edited, as its score can change), not on deletes. Progress is the highest count ever reached (`Math.Max` with the stored value), so deleting content never lowers it, and deleting and recreating content doesn't raise it until the count beats the old peak. Unlocks are permanent. It never throws: failures are logged and swallowed, so the triggering action still succeeds. Counting rules live in `AchievementService.CountAsync` and are mirrored by the backfill SQL in the `AddAchievements` migration — reviews of every visibility count, replies exclude soft-deleted ones, low score is `Score <= 5.0`, and collections exclude the default `Favourites` (`Collection.DefaultName`). A new metric needs a case there and a hook where its data changes.
  - **Unlock delivery**: newly unlocked tiers go to every registered `IAchievementUnlockHandler`. `ResponseHeaderUnlockHandler` writes them (only for the requesting user) to the `X-Unlocked-Achievements` response header as JSON; the header is exposed in the CORS policy. `NotificationUnlockHandler` stores one notification per tier. Add a new handler instead of changing the service. `GET api/Achievement/{username}` is public.
- **Notifications**: `Notification` (recipient cascade, nullable actor `Restrict`) stores ready-to-display `Title`/`Message` plus a navigation target as plain ints/strings without FKs (`ReviewID`, `ReplyID`, `GroupCode`), so it outlives deleted content (the link then shows a not-found state). Types (`NotificationType`): `System`, `ReviewReply`, `ReplyReply`, `AchievementUnlocked`, `NewFollower`, `SubscriptionStarted`, `PaymentFailed`, `SubscriptionCancelled`, `SubscriptionEnded` (the last four route to the Premium page on both clients). Create them through `INotificationService` (`CreateAsync`, `CreateSystemAsync`, `NotifyNewFollowerAsync`) after the triggering `SaveChangesAsync`; like achievements, creation never throws. Hooks: `ReviewReplyService.CreateReplyAsync` (review author for layer 2, parent reply author for layer 3; never self, never a deleted parent, only if the recipient can still see the review), `FollowerService.FollowUserAsync` (deduplicated per actor for 7 days), the unlock handler, and `SecurityService`/`UserService` system messages. `NotificationController` (`api/Notification`, own notifications only — someone else's is a 404) lists with keyset paging (`status`, `sort`, `afterId`), has a cheap `unseen-count` for the badge polling, and mark seen/unseen, mark all seen, delete, delete all seen. Max 200 per user (oldest seen dropped first). A new type needs an enum value, a creation call where its data changes, and a route in `src/utils/notifications.ts`.
- **Single review / reply**: `GET api/Review/{id}` (with author, hidden == 404) and `GET api/ReviewReply/{id}` (the reply plus its layer-2 parent, deleted == 404) back the `/review/:reviewId?reply=` deep links.
- **Recent reviews**: `GET api/Review/recent?count=` (anonymous, 1–20, default 10) returns the newest public reviews that have some written text, with author and media; it feeds the Android home page (the web app doesn't use it).
- **Email**: `IAccountEmailService` builds the account emails (`EmailTemplates`: one inline-styled HTML layout + plain-text part, every value HTML-encoded) and only enqueues them on the singleton `EmailQueue` (bounded `Channel`); `EmailDispatcherService` (hosted) sends them with `SmtpEmailSender` (MailKit, `EmailOptions` from the `Email` section) with a couple of retries. Queued mail is lost on restart, which is fine because every email-dependent flow has a resend. Never log email bodies (they contain tokens/codes).
- **Background cleanup**: `DataCleanupService` (hosted, daily) deletes seen notifications older than 90 days and spent/expired `SecurityToken` rows.
- **DTOs**: Request/response shapes live in `DTOs/`, kept separate from EF entities; controllers should not return entities directly.

### Frontend

- **Preact, not React**: the project uses `preact/compat` aliased to `react`/`react-dom` (see `tsconfig.json` paths and `vite.config.ts`'s `@preact/preset-vite`). Write components using standard React/JSX patterns and hooks from `preact/hooks` — they compile through the compat layer.
- **Routing**: all routes are declared in `src/App.tsx` (`AppRoutes`) using `react-router-dom`; `src/index.tsx` only renders `App`. Most top-level pages are wrapped in `PageContainer` (shared header/footer/theme chrome). The `/profile/:username` route is a layout route (`ProfileLayout`) with nested tab routes (`overview`, `reviews`, `collections`, etc.) rendered inside it.
- **Auth state**: global auth state is provided by `AuthContext`/`AuthProvider` (`src/context/AuthContext.tsx`), backed by `AuthService` (`src/services/AuthService.ts`), which calls the API with `credentials: 'include'` so the httpOnly JWT cookie is sent automatically. Do not attempt to read or store the JWT in JS — the cookie is httpOnly by design. `AuthContext` registers a handler with `apiClient.ts` so that any 401 response clears the logged-in user (e.g. after the session was revoked from another device). `AuthUser.isEmailConfirmed` drives the non-blocking `EmailVerificationBanner` (in `PageContainer`); call `refreshUser()` after anything that changes it. `LoginPage` has a second step for 2FA logins (code, resend with cooldown, back).
- **Services layer**: each backend controller has a matching `src/services/*.ts` file (`AuthService`, `MediaService`, `ReviewService`, `CollectionService`, `FollowerService`, `UserService`, `ReviewReplyService`, `AchievementService`, `NotificationService`, `SecurityService`, `SubscriptionService`) that wraps the API calls. They use `apiFetch` from `src/services/apiClient.ts` (a thin `fetch` wrapper that reports 401s to `AuthContext`) — use `apiFetch`, not plain `fetch`. New backend endpoints should get a corresponding method here rather than calling the API directly from components/pages.
- **Review replies UI**: `ReviewCard` renders a collapsed `ReplyThread` (layer 2) whose `ReplyItem`s load their own layer-3 children; both lists use the `useReplyList` hook (`src/hooks/`). `ReplyForm` validates with `isValidReply`/`MAX_REPLY_LENGTH` from `src/utils/validation.ts`. Counts and placeholders are updated locally after create/delete instead of refetching.
- **Achievements UI**: the profile `achievements` tab (`AchievementsTab`) loads every achievement once and filters/sorts client-side; the filter state (`status`, `category` — both repeatable — and `sort`) lives in the URL. `AchievementFilterBar` is sticky from `md` up. `AchievementCard` is a CSS 3D flip card (keyboard operable, no animation under `prefers-reduced-motion`), greyed out until a tier is earned. Icons are `public/achievements/<IconKey>.svg` (placeholder art, falls back to a trophy icon). Status/sort helpers and tier colours are in `src/utils/achievements.ts`. Unlock toasts need no per-component code: `apiFetch` reads the `X-Unlocked-Achievements` header and passes it to `AchievementToastProvider` (`src/context/AchievementToastContext.tsx`), which queues the toasts.
- **Notifications UI**: `NotificationProvider` (`src/context/NotificationContext.tsx`, inside `AuthProvider`) holds the unseen count: loaded on login, polled every 45s while the tab is visible, and refreshed shortly after any successful non-GET `apiFetch` (the user's own actions can notify them). `NotificationBell` in the `Header` opens `NotificationsDialog` (Seen/Unseen toggles, sort, mark all seen, delete all seen with confirmation, "load more", full screen on small screens) with `NotificationCard`s; actions update the list and badge optimistically and roll back on failure. "Take me there" marks the notification seen and navigates to the route from `getNotificationRoute` (`src/utils/notifications.ts`). Reply notifications open `ReviewPage` (`/review/:reviewId?reply=`), which passes a `replyFocus` through `ReviewCard` -> `ReplyThread` -> `ReplyItem` to seed, expand, scroll to and highlight that reply.
- **Email links**: `EmailLinkPage` serves `/verify-email` and `/confirm-email-change`; it POSTs the `token` query param once on mount.
- **Premium**: `PremiumPage` (`/premium`, also for anonymous visitors) shows Free vs Premium from `GET Subscription/plan`, the Subscribe button (redirects to the provider's checkout URL), the placeholder "early access" preview and, for subscribers, `SubscriptionPanel` (status chips, dates, cancel with `CancelSubscriptionDialog`, resume, "Manage payment details" = the provider's portal). The same panel is the `SubscriptionDialog` of `AccountSettingsMenu`. `SubscriptionReturnPage` (`/subscription/return?status=`) never trusts the redirect: it calls `sync` once, then polls the status (2 s, max 30 s) and `refreshUser()`. `AuthUser` has `tier`, `isPremium`, `entitlements` (`hasFeature` in `src/utils/subscription.ts`, UI only). Any 402 from `apiFetch` goes to `PremiumUpsellContext` (inside the router), which refreshes the user and opens the "This is a Premium feature" dialog; `PremiumUpsell` is the inline variant for locked features. `PremiumBadge` (gold, `PREMIUM_COLOR`) shows on profiles with `isPremium`; the header has a Premium link and a gold avatar ring for subscribers. Locale-formatted dates can end with a dot, so they never end a sentence in the UI.
- **Account settings**: the owner-only `AccountSettingsMenu` on the profile header (rendered by `ProfileLayout`) opens the `ChangeUsernameDialog`, `ChangeEmailDialog`, `ChangePasswordDialog`, `SecurityDialog` (verification state + resend, pending email change + cancel, 2FA enable/disable) and `LogoutAllDialog`. Change email/password require the current password; client-side validation helpers (`isValidEmail`, password length limits) live in `src/utils/validation.ts`.
- **Theming**: light/dark mode is managed in `src/App.tsx` (`useThemeMode`, `AppProviders`) via MUI's `ThemeProvider`/`createTheme`, persisted to `localStorage`, and toggled through `PageContainer`.

### Android

Package `com.reviewapp.android` (`review-app-android/app/src/main/java/...`). MVVM with a manual DI container; it follows the web app's behavior and the `wireframes_mobile/` design.

- **DI**: `di/AppContainer.kt` (created in `ReviewApplication`) builds OkHttp, Retrofit, the APIs, repositories and `SessionManager` once. ViewModels get them through `viewModelFactory { initializer { appContainer()... } }` in their companion `Factory`; route arguments come from `createSavedStateHandle().toRoute<...>()`.
- **Layers**: `data/remote` (one Retrofit interface per controller in `Apis.kt`, `@Serializable` DTOs in `dto/Dtos.kt` with `toDomain()` mappers, note the API's `externalApiID` casing) → `data/repository` (`AuthRepository`, `MediaRepository`, `ReviewRepository`, `UserRepository`, `CollectionRepository`, `ReplyRepository`, `NotificationRepository`, `AchievementRepository`, `AccountRepository`, `SubscriptionRepository`) → `ui/<feature>` (Screen + ViewModel exposing `StateFlow` UI state and one-off events through a `Channel`). Domain models are in `domain/model`. New endpoints get a method in the matching `*Api` interface and repository, not direct calls from ViewModels.
- **Errors**: wrap calls in `apiCall { }` → `ApiResult` (`Success`/`Error(message, code)`). `ApiErrors.message` picks `{ error }`, then the first `ValidationProblemDetails` message, then a generic one per status code.
- **Session**: the same httpOnly JWT cookie as the web app. `data/local/SecureCookieJar` is the OkHttp `CookieJar`; it keeps `__Host-jwt_token` across restarts, encrypted with an Android Keystore AES-GCM key (`CryptoStore`) in the `session` DataStore (excluded from backups). Never read or log the token. `SessionManager` holds `AuthState` (`Loading`/`LoggedOut`/`LoggedIn(user)`), restores it on start with `GET Auth/check-auth`, and an OkHttp interceptor sends every 401 to `onUnauthorized()` (like `apiFetch` on the web), so revoked sessions log out on their next request. A second interceptor handles the other response side effects: an `X-Unlocked-Achievements` header goes to `AchievementRepository.onUnlockHeader`, and every successful non-GET request calls `NotificationRepository.onMutation()`. A password change re-issues the cookie in its response, and `saveFromResponse` replaces the stored one, so this device stays logged in while every other session is revoked.
- **Navigation**: type-safe Navigation Compose routes in `ui/navigation/Routes.kt`, wired in `AppNavHost.kt`. The bottom bar tabs (Home, Movies, Series, Music, Profile) each keep their own back stack. Login is pushed on top of the screen that needed it and pops back after success. The Profile tab (`MyProfileRoute`) and any user's page (`ProfileRoute(username, tab?)`, `tab` being a `ProfileTab` name to open on) share `ui/profile/ProfileScreen`/`ProfileViewModel`; without a route username it follows the logged-in user and shows a login prompt when logged out. Other profiles, follow lists, collections, user search, review pages, the notifications screen and the account settings are pushed onto the current tab's stack.
- **Lists**: infinite scroll with `ui/PagedLoader` (page-based endpoints, de-duplicates by key, retry, `remove` for local deletes) and `InfiniteListEffect`. Media cards load their average score lazily through `ReviewRepository.requestStats` (shared cache, at most 4 parallel requests). `MediaRepository` caches every media it returns, so the details screen opens without refetching. Review list filters (`ReviewsHeader`, `ReviewFilterChips`, `ScoreRangeSheet`) are shared in `ui/components/ReviewFilters.kt`.
- **Change events**: repositories emit `SharedFlow`s so other screens refresh without refetching everything: `ReviewRepository.changes` (review saved or deleted, deletions carry the review id; details, home and the owner's profile), `ReplyRepository.replyCountChanges` (review cards patch their reply count through `PagedLoader.update`), `UserRepository.followChanges` (profile header counts) and `CollectionRepository.changes` (profile collections tab, collection screen).
- **Review page and replies**: tapping any review card opens `ReviewRoute(reviewId, replyId?)` (`ui/review/ReviewScreen`, the web's `ReviewPage`): the review, its reply thread and a reply bar at the bottom ("Replying to X" for a layer-3 reply). The thread lives in the pure `ReplyThreadState` (`ui/review/ReplyThreadState.kt`, unit-tested) with the web's rules: keyset pages merged by id with the cursor from the server's last item, a deleted layer-2 reply with children stays as a placeholder, a placeholder whose last child is deleted disappears, and `replyCount` covers both layers. `replyId` seeds the thread with that reply (and its parent), highlights it and scrolls to it; a deleted or hidden one shows a notice. The same route is a deep link, `reviewapp://review/{reviewId}?replyId={replyId}` (`adb shell am start -d "reviewapp://review/12?replyId=34"`), meant for notifications.
- **Profile**: the header (avatar URL dialog, follower counts, follow button, inline bio edit) and the Reviews / Collections / Achievements tabs (no Overview yet) are one `LazyColumn`; the tab row and the active tab's filters are a single `stickyHeader`, because several sticky headers push each other away. Follow/unfollow and remove-follower are optimistic and roll back on failure. The owner's settings icon opens the account settings. When the logged-in user is renamed, the Profile tab follows the new name (a pushed `ProfileRoute` with the old name doesn't).
- **Notifications**: `NotificationRepository` holds the unseen count (`unseenCount`, 0 while logged out; responses from an earlier session are dropped). It is refreshed on login, by `NotificationPollingEffect` in `ReviewAppRoot` (every 45 s while the app is at least STARTED, and at once when it comes back to the foreground; in-app only, no system notifications) and 800 ms after the user's own writes (`onMutation`, debounced). The activity-scoped `NotificationBadgeViewModel` feeds the Home top bar's `NotificationBell` (hidden when logged out) and a dot on the Home tab. `NotificationsRoute` (`ui/notifications/NotificationsScreen`, the web's `NotificationsDialog` full screen as in the wireframe) pages with the keyset cursor (20 per page, infinite scroll), has Seen / Unseen chips (exactly one on filters, both or neither = all) and a sort, and its actions are optimistic with rollback; the list rules are in the pure, unit-tested `NotificationListState`. "Take me there" goes through `notificationTarget` (same mapping as the web's `getNotificationRoute`): replies to `ReviewRoute(reviewId, replyId)`, new followers to their profile, unlocks to the user's own `ProfileRoute(me, Achievements)`. A new `NotificationType` needs an enum value (unknown names show as `System`) and a case there.
- **Achievements**: the profile's Achievements tab loads `GET Achievement/{username}` on first open and filters/sorts locally with `util/Achievements.kt` (mirrors `src/utils/achievements.ts`: overlapping statuses, OR within a group and AND across, stable "Unlocked first" sort; unit-tested). Each card is an `AchievementRow` (wireframe layout: icon and tier medals, next tier's goal and progress, greyscale while locked). The icons are vector drawables hand-converted from `review-app/public/achievements/*.svg` (`res/drawable/achievement_<key>.xml`, mapped in `achievementIcon`, trophy fallback), so a new or changed SVG must be converted too. Unlocks from the response header are queued by the activity-scoped `UnlockBannerViewModel` and shown one at a time by `UnlockBannerHost` (5 s, top of the screen, tap opens the Achievements tab); the owner's open tab reloads after an unlock.
- **Collections and favourites**: `CollectionRepository.mine` (`MyCollections`) caches the logged-in user's collections and memberships (`GET Collection/me/memberships`, keyed by media key), loaded on login and cleared on logout, so the heart is a real Favourites toggle and the add-to-collection sheet shows checkmarks. Membership changes are optimistic, serialized with a mutex, and reverted and reloaded on failure. `ui/collection/CollectionActions.kt` holds an activity-scoped `CollectionActionsViewModel` that `CollectionActionsHost` (around the nav host in `ReviewAppRoot`) provides through `LocalCollectionActions`; `MediaCollectionButtons` reads it, so any media card shows the buttons for logged-in users without extra parameters, and errors go to the root snackbar. The collection screen reorders with `sh.calvin.reorderable` (long-press drag in a `LazyVerticalGrid`): the list moves locally and one `PUT reorder` is sent on drop with the item's final index.
- **Premium**: `PremiumRoute` (`ui/subscription/PremiumScreen`, the web's `PremiumPage`: plans, subscribe, the subscription card with cancel/resume/payment details, the early access preview) is opened from the account settings' Subscription section (the inline `PremiumUpsell` for Free users), notifications and the 402 upsell. Payment pages open in the browser (`LocalUriHandler`); the provider returns through the API's `return/android` page to `reviewapp://subscription/{result}` = `SubscriptionReturnRoute` (`SubscriptionReturnScreen`: waits for the session, `awaitPremium` = `sync` then polling). `MainActivity` is `singleTask`, and `ReviewAppRoot` sends deep links of new intents to `navController.navigate(uri)` (`handleDeepLink` would restart the task for the browser's NEW_TASK intents); cold starts use the graph's deep links. Test with `adb shell am start -d "reviewapp://subscription/success"`. A third OkHttp interceptor reports 402s to `SubscriptionRepository.onPremiumRequired()` (refreshes the user), and the activity-scoped `PremiumRequiredHost` shows the dialog. `AuthUser.isPremium` / `entitlements` / `hasFeature` come from check-auth; the repository refreshes the user after every subscription change. The card's rules (chips, date label, which actions) are the pure, unit-tested `subscriptionView` in `ui/subscription/SubscriptionUi.kt`. `PremiumBadge` shows next to the username on profiles with `isPremium`.
- **Theme**: fixed MUI-like palette (no dynamic color) in `ui/theme`, plus `AppTheme.extendedColors` (success/warning, pros/cons boxes) and `ScoreTier.color()`. Score thresholds, validation limits and filter values live in `util/` and mirror the web app (`Format.kt`, `Validation.kt`, `DiscoverOptions.kt`). The theme mode (system/light/dark) is stored by `SettingsStore`.
