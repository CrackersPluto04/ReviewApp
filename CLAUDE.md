# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a three-project repo with no shared root tooling — each part is built/run independently:

- `ReviewApp.Api/` — ASP.NET Core 8 Web API (C#), EF Core + SQL Server backend.
- `ReviewApp.Api.Tests/` — the backend test suite (xUnit + Shouldly + NSubstitute): unit, service integration (real SQL Server) and in-process HTTP tests, see "Backend tests" below. A sibling folder because the web SDK project would compile any `.cs` below `ReviewApp.Api/`. It is in `ReviewApp.Api/ReviewApp.Api.sln`, so `dotnet test ReviewApp.Api.sln` from `ReviewApp.Api/` runs it.
- `review-app/` — Preact + TypeScript frontend (built with Vite), using MUI for components and react-router-dom for routing. Its test suite (Vitest) is in `review-app/tests/`, see "Frontend tests" below.
- `review-app-android/` — native Android client (Kotlin, Jetpack Compose + Material 3), being brought up to the web app's feature set milestone by milestone. Mobile wireframes are in `wireframes_mobile/` (gitignored, local only).

## Common commands

### Backend (`ReviewApp.Api/`)

Run all commands from `ReviewApp.Api/`.

```
dotnet run                          # run with default (http) launch profile
dotnet run --launch-profile https   # run with HTTPS (matches frontend CORS origin)
dotnet build
dotnet ef migrations add <Name>     # add a new EF Core migration
dotnet ef database update           # apply migrations to local DB
```

- Swagger UI is served at `/swagger` in Development.
- HTTPS profile listens on `https://localhost:7140` (also `http://localhost:5062`); the frontend's API clients are hardcoded to `https://localhost:7140`, so run the API with the `https` profile when working end-to-end with the frontend. The CORS origin and the links in emails come from `App:FrontendBaseUrl` (`https://localhost:5173` in `appsettings.json`); `Program.cs` refuses to start without it.
- Local connection strings and third-party API keys (TMDb, Spotify) live in `appsettings.Development.json`, which is gitignored (not committed) — each developer creates their own copy locally. The same goes for real SMTP credentials (`Email` section).
- **Subscriptions in development**: the committed `Subscription:Provider` is `Fake` (no payment, no account: "checkout" activates a 30 day subscription at once; only allowed in Development, `Program.cs` refuses to start with it elsewhere). `POST /api/Subscription/dev/simulate` (Development only) plays `PaymentFailed`, `Renewed`, `Ended` or `Lapsed` (period over without a notification, for the expiry job) against the current user's fake subscription. For Stripe test mode set `Subscription:Provider` to `Stripe` and `Stripe:SecretKey`, `Stripe:WebhookSecret`, `Stripe:PriceId` (a monthly EUR price) in `appsettings.Development.json` (the API refuses to start without them), then forward webhooks with the Stripe CLI: `stripe listen --all-snapshot --forward-to https://localhost:7140/api/Subscription/webhook --skip-verify` (newer CLIs require `--all-snapshot` or an `--events` list; event types the API doesn't handle are acknowledged and ignored; its `whsec_...`, also printed by `stripe listen --print-secret`, is the webhook secret), pay with the test card `4242 4242 4242 4242`. Without the CLI the return pages' `sync` still picks the subscription up. The displayed price (`Subscription:PriceAmount`/`Currency`) must match the Stripe price.
- **Camera recognition in development**: the committed `Recognition` section uses `Provider` `Gemini` (model `gemini-3.8-flash`, `ThinkingLevel` low, `FallbackModels` `gemini-3.5-flash` then `gemini-3.5-flash-lite`) and needs `Gemini:ApiKey` in `appsettings.Development.json` (a Google AI Studio key; the API refuses to start without it while `Recognition:Enabled` is true). The free tier may use submitted photos to improve Google's products, so use it only for your own test photos; a deployment needs a key of a billing-enabled project. `Recognition:Provider` `Fake` (Development only) answers every photo with a canned "Iron Man statue" without an AI call, which still exercises TMDb / Spotify, ranking and paging. A model that answers 503 "high demand" (common for new models, even for a text-only request: capacity, not our request), 429, a 5xx or times out is swapped for the next fallback at once (logged as `falling back to ...`). Settings can be overridden per run with environment variables, e.g. `Recognition__Model=gemini-3.5-flash-lite` or `Recognition__FallbackModels__0=...`. `Recognition:Enabled` false switches the feature off (503, the clients show "temporarily unavailable"). The token counts of each call are logged (`Gemini tokens: ...`), never the photo or the answer.
- **Emails in development**: the committed `Email` settings point to a local SMTP catcher on `localhost:1025` without auth (e.g. Mailpit, web UI on `http://localhost:8025`). Without one running, sending just fails in the background (logged), the API keeps working. To send real emails, override `Email` (Host, Port, Security = `StartTls`/`SslOnConnect`, Username, Password, FromAddress) in `appsettings.Development.json`.

### Backend tests (`ReviewApp.Api.Tests/`)

Run from `ReviewApp.Api/`. The only prerequisites are the .NET SDK and SQL Server LocalDB (no Docker, no local settings file, no network).

```
dotnet test ReviewApp.Api.sln                                                   # everything
dotnet test ReviewApp.Api.sln --filter "FullyQualifiedName~Tests.Integration"   # one layer: Tests.Unit / Tests.Integration / Tests.Http
dotnet test ReviewApp.Api.sln --filter "FullyQualifiedName~ReviewServiceTests"  # one feature
dotnet test ReviewApp.Api.sln --settings ../ReviewApp.Api.Tests/coverage.runsettings --collect "XPlat Code Coverage"
reportgenerator -reports:../ReviewApp.Api.Tests/TestResults/*/coverage.cobertura.xml -targetdir:../coverage-report   # optional HTML report (dotnet tool install -g dotnet-reportgenerator-globaltool)
```

- **Layers** (folders = namespaces): `Unit/` (pure logic, no database), `Integration/` (the real services from the app's own DI container against a real database, external systems faked), `Http/` (requests through the whole pipeline: auth cookie, rate limits, filters, model binding, status codes). The two older `Subscription*Tests.cs` files in the root are unit tests too. No coverage threshold is enforced.
- **Database**: `Support/TestDatabase` creates one throwaway database per run (`ReviewAppTests_<guid>`, collation pinned to `SQL_Latin1_General_CP1_CI_AS`) through the real migrations, so the triggers, constraints and seeds exist, and drops it on exit (leftovers older than a day are dropped by the next run). LocalDB by default; `REVIEWAPP_TEST_SQL` (a server connection string without database) points to another server, which CI uses. Tests never touch `ReviewAppDb`. They run in parallel in that one database and stay isolated by creating uniquely named data through the `Support/TestData` builders (`TestData.Unique`); never insert the `Favourites` collection (the trigger does), look it up with `FavouritesAsync`. Tests of the expiry and cleanup jobs, which work on every row, are in the non-parallel `GlobalJobsCollection`.
- **Test host**: `Support/ApiFactory` (`WebApplicationFactory<Program>`, so `Program.cs` ends with `public partial class Program`) runs the app in the `Testing` environment, so `appsettings.Development.json` is never loaded and the run is the same as on CI. Settings go in with `UseSetting` (Program.cs reads them eagerly); it uses Stripe with dummy keys only to pass startup validation and replaces `IPaymentProvider` with `TestPaymentProvider` (the Fake provider's behaviour, plus webhooks signed with `TestPaymentProvider.ValidSignature` and per-user outages). TMDb / Spotify are `FakeTmdbService` / `FakeSpotifyService` (their recognition lookups find every title by default, with a stable ID per title; `ScriptTitle` / `FailTitle` / `ScriptCollection` / `ScriptPerson` change that per unique title). Camera recognition registers Gemini with a dummy key, replaced by `TestRecognitionProvider` (`App.Recognition`): it answers by a tag that `TestImages.Jpeg(tag)` writes into the test photo (header-only JPEG / PNG / HEIC bytes), so parallel tests never share answers; `Answer` / `AnswerRaw` / `Fail` / `Hold` script it, `Calls(tag)` counts AI calls; HTTP tests upload with `Photo(bytes)` (multipart). `new ApiFactory(settings: ...)` starts a host with other configuration (e.g. the feature switched off). The cleanup and expiry hosted services are removed (their work is called directly: `DataCleanupService.CleanupAsync` is internal, `InternalsVisibleTo` the tests); the email dispatcher keeps running and delivers into `CapturingEmailSender` (`App.Mail.WaitForAsync(recipient, subject)`, `LinkToken` / `Code` read the emailed token or 2FA code). `ApiFactory.Shared` is one host for the whole run, started inside its `Lazy` (WebApplicationFactory starts the server on first use without a lock, so parallel first uses could build two hosts with separate singletons).
- **HTTP tests**: `As(user)` sends a hand-minted session cookie (`Support/TestTokens`), `Browser()` keeps real cookies for login flows (HTTPS base address, so the `Secure` `__Host-` cookie works). `RateLimiting:PermitMultiplier` (default 1, read in `Program.cs`) is 1000 in the shared host; `RateLimitTests` start their own host with the real limits. `Support/PremiumProbeController` is a test-only `[RequiresFeature]` endpoint, so the paywall tests don't depend on any real feature.
- **Findings**: `ReviewApp.Api.Tests/FINDINGS.md` lists the bugs the suite found: fixed ones (their tests are regression tests) and open ones, each with a skipped test (`Skip = "Known issue Fx (FINDINGS.md) ..."`) describing the correct behaviour. Un-skip it when fixing the issue.
- **CI**: `.github/workflows/backend-tests.yml` runs the suite on pull requests and pushes to `main` that touch the backend or the tests (or by hand, `workflow_dispatch`), on Ubuntu with a SQL Server service container, no secrets; test results and coverage are uploaded as an artifact.
- **New backend features come with tests**: pure rules as unit tests, the service behaviour as integration tests (happy path, failures, ownership / visibility), and new endpoints in the HTTP smoke tests. A new external system gets a fake in `Support/` and a replacement in `ApiFactory`.

### Frontend (`review-app/`)

Run all commands from `review-app/`.

```
npm start      # vite dev server, https on port 5173, opens browser
npm run build  # production build
npm run preview
npm run typecheck  # tsc --noEmit over src/ and tests/
```

- The dev server uses `@vitejs/plugin-basic-ssl`, so it always serves over HTTPS on `https://localhost:5173` — this must match the CORS origin allowed by the API.

### Frontend tests (`review-app/tests/`)

Run from `review-app/`. The only prerequisite is Node (no backend, no browser, no network).

```
npm test                                   # everything (vitest run)
npm test -- tests/pages/LoginPage.test.tsx # one file; -t "<name>" for one test
npm run test:watch                         # watch mode
npm run test:coverage                      # + coverage (coverage/index.html, cobertura) and test-results/junit.xml
KNOWN_ISSUES=1 npm test                    # runs the known-issue tests as expected failures (see Findings)
npm test -- --sequence.shuffle             # random order, to catch tests that depend on each other
```

- **Stack**: Vitest + jsdom + Testing Library for Preact (`@testing-library/preact`, `user-event`, `jest-dom`) + MSW for the network. Config in `vitest.config.ts`, separate from `vite.config.ts`. `globals: false`, so tests import `describe`/`it`/`expect`/`vi` from `vitest`.
- **Preact as React**: the config aliases `react`/`react-dom`/`react/jsx-runtime` to `preact/compat`, inlines MUI, Emotion, react-router, dnd-kit and react-transition-group (`server.deps.inline`) and resolves their ESM builds (`mainFields` / `conditions`). Real `react` 19 is installed as their peer dependency; any CJS build that `require()`s it brings in a second renderer ("object is not extensible", "Invalid hook call"). `tests/support/environment.test.tsx` guards this, look there first if MUI suddenly fails to render.
- **Layout** mirrors `src/`: `utils/`, `hooks/`, `services/`, `context/`, `components/`, `pages/` with one `Foo.test.tsx` per source file, plus `App.test.tsx` (the route table of `src/App.tsx`). `src/index.tsx` only calls `render(<App />)`; `App.tsx` exports `App`, `AppProviders` (theme, auth, notifications, toasts) and `AppRoutes` (upsell + route table) so tests can mount them under a `MemoryRouter`.
- **Support** (`tests/support/`): `server.ts` (the MSW server, default handlers: anonymous `check-auth`, unseen count 0), `api.ts` (`apiUrl`, `capture(method, path, response)` records what was sent (URL, body, `credentials`, headers), response helpers `ok`/`apiError`/`validationProblem`/`htmlError`/`networkError`/`paymentRequired`, `deferred()` for loading states), `builders.ts` (DTO builders), `handlers.ts` (endpoints many components hit: media stats, replies, collections), `render.tsx` (`renderWithApp(ui, { user, route, path })` = the app's providers + router, `renderApp(route)` = the whole app, `currentLocation()`, `loginAs`, `useFakeTimers`), `browser.ts` (stubs for `location`, `confirm`/`alert`, `matchMedia`, visibility, `muteConsoleError`). `services/endpoint.ts` generates the standard tests of a service method (request, success, `{ error }`, fallback, network failure, non-JSON error).
- **Network rule**: every request needs a handler; one without fails the test after it ends (the services swallow fetch errors, so MSW's own error mode wouldn't). Requests still running at the end of a test are awaited, and after the file the network is closed, so nothing ever reaches `localhost:7140`.
- **Timers**: `useFakeTimers()` fakes timers that still move with real time (findBy / waitFor keep working); `useFakeTimers(undefined, { frozen: true })` + `paint()` / `flush()` for exact timing (debounce). Preact runs effects after the next frame (or 35 ms): advance timers **outside** `act()` when a chain of effects must run (inside `act` it holds every effect until it ends).
- **Locale / time zone**: the app formats with the browser's default locale; the setup pins `en-US` and UTC (`tests/support/locale.ts`) because Node on Windows ignores `LANG`, so results are the same on every machine and CI.
- **jsdom gaps**: no layout (dnd-kit drops are simulated by capturing `onDragEnd`, see `CollectionDetails.reorder.test.tsx`), `scrollIntoView`/`scrollTo` are mocks, `confirm`/`alert`/`location.href` are stubbed per test. MUI Dialogs hide the rest of the page from role queries while open; several selects have no accessible name, query them by the value they show.
- **Findings**: `review-app/tests/FINDINGS.md` lists the bugs the suite found (W1-W19, none fixed by decision), each with skipped tests written with `knownIssue('Wx', ...)` that describe the correct behaviour. Fixing one = turn it into a plain `it`, make it pass, move the finding to "Fixed".
- **CI**: `.github/workflows/frontend-tests.yml` runs on pull requests and pushes to `main` touching `review-app/` (or by hand, `workflow_dispatch`): `npm ci`, type check, tests with coverage, production build; results and coverage are uploaded as the `frontend-test-results` artifact. No secrets. Half the cores are used (`maxWorkers: '50%'`, each jsdom worker is heavy), the full run takes about 3 minutes.
- **New frontend features come with tests**: new service methods through `describeEndpoint`, components and pages with their happy path, failure path, logged-out / not-owner state and loading / empty states, new routes in `App.test.tsx`.

### Android (`review-app-android/`)

Run all commands from `review-app-android/` (Windows: `gradlew.bat`). Gradle needs a JDK 17+; Android Studio's bundled one works (`JAVA_HOME="C:\Program Files\Android\Android Studio\jbr"`).

```
gradlew assembleDebug         # build the debug APK
gradlew installDebug          # install on the running emulator/device
gradlew testDebugUnitTest     # JVM unit tests (validation, formatting, API JSON parsing)
gradlew connectedDebugAndroidTest # instrumented tests on the running emulator/device (the encrypted offline database); uninstalls the app afterwards (its session and offline copy go), add -Pandroid.injected.androidTest.leaveApksInstalledAfterRun=true to keep it
adb reverse tcp:7140 tcp:7140 # once per emulator/device boot, see below
adb reverse tcp:5062 tcp:5062 # same, for the checkout return page in the browser
```

- **Reaching the local API**: the app calls `BuildConfig.API_BASE_URL` = `https://localhost:7140/api/` (set in `app/build.gradle.kts`). `adb reverse` forwards the device's `localhost:7140` to the dev machine, so the hostname matches the ASP.NET dev certificate (works for the emulator and USB devices). Run the API with the `https` profile (it serves both 7140 and 5062).
- **Checkout return page**: after paying in the device's browser, the provider sends the user to `http://localhost:5062/api/Subscription/return/android` (`Subscription:MobileReturnBaseUrl`), which opens `reviewapp://subscription/{result}`. Plain HTTP because the browser doesn't trust the dev certificate (the app does, through `network_security_config`); in Development that path is exempt from the HTTPS redirect (`UseHttpsRedirectionForApi`). It needs the second `adb reverse` (5062). Deployed, `MobileReturnBaseUrl` must be the public HTTPS API URL.
- **Dev certificate**: debug builds trust the ASP.NET dev cert through `app/src/debug/res/xml/network_security_config.xml` (`<debug-overrides>`), which points to `app/src/debug/res/raw/aspnet_dev_cert.pem`. That file is per developer and gitignored, so export it once. The PEM export also writes the **private key**, so export outside the project and copy only the `.pem` (anything in `res/raw` is packaged into the APK):
  ```
  dotnet dev-certs https --export-path %TEMP%\aspnet_dev_cert.pem --format Pem --no-password
  copy %TEMP%\aspnet_dev_cert.pem app\src\debug\res\raw\
  del %TEMP%\aspnet_dev_cert.pem %TEMP%\aspnet_dev_cert.key
  ```
  Release builds trust only the system CAs. Without the file the debug build fails (`resource raw/aspnet_dev_cert not found`).
- **CI**: `.github/workflows/android-tests.yml` runs on pull requests and pushes to `main` touching `review-app-android/` (or by hand, `workflow_dispatch`): JDK 25 (the daemon JVM in `gradle/gradle-daemon-jvm.properties`), Gradle cache (`cache-provider: basic`), a throwaway self-signed `aspnet_dev_cert.pem` (key discarded) so the debug resources link, then `testDebugUnitTest assembleDebug`; test results and the HTML report are uploaded as the `android-test-results` artifact. No emulator (the `androidTest` suite, which needs a device for SQLCipher's native library, is run locally), no secrets.
- `libs.versions.toml` holds all dependency versions. AGP 9 has built-in Kotlin, so the `kotlin-android` plugin entry is not applied.
- **Room and KSP**: Room runs through KSP2 (`com.google.devtools.ksp`, versioned independently of Kotlin; it works with AGP's built-in Kotlin). The Room Gradle plugin exports every `OfflineDatabase` schema version to `app/schemas/` (committed, the base of migration tests). `kotlinx-coroutines-test` is pinned to the coroutines version the app resolves (Room, lifecycle), so unit tests run on the same coroutines core as the app. On Windows a scanner (Defender, SonarLint) can lock KSP's incremental caches ("A folyamat nem fér hozzá a fájlhoz" / "used by another process" under `build/kspCaches`); `gradlew ... -Pksp.incremental=false` avoids them.
- **Offline database** (`data/local/offline/OfflineDatabase`): Room on SQLCipher (`net.zetetic:sqlcipher-android`, `SupportOpenHelperFactory` with a raw 32 byte key; `OfflineDatabase.open` loads the native library once). The AAR ships its own R8 keep rules and adds about 2 MB of native code per ABI. Version 1 is still being shaped while offline mode is built; once released, schema changes need an explicit migration, never a destructive one (the outbox holds changes that exist nowhere else).
- **Testing offline mode on the emulator**: `adb reverse` tunnels through adb, so airplane mode alone (`adb shell cmd connectivity airplane-mode enable`) shows the app as offline but the API still answers. To make the backend unreachable as well, also run `adb reverse --remove tcp:7140` (and `adb reverse tcp:7140 tcp:7140` again to come back). A Premium test account without Stripe: run the API with `Subscription__Provider=Fake` (Development only), then `checkout` + `sync`.

## Architecture

### Backend

- **Layering**: `Controllers/` → `Services/` (business logic, interfaces in `Services/Interfaces/`) → `DAL/` (EF Core `AppDbContext` + `Entities/`). Controllers depend on service interfaces, which are registered as scoped in `Program.cs`.
- **Auth**: JWT bearer auth, but the token is normally delivered via an httpOnly cookie (`__Host-jwt_token`, `Secure`, `SameSite=Strict`, `Path=/`) rather than the `Authorization` header — see the `OnMessageReceived` handler in `Program.cs` that pulls the token from the cookie. `UserAuthHelper` (`IUserAuthHelper`) reads the authenticated user's ID from the `"id"` claim; use `GetSecureUserID()` in endpoints that require auth and `GetOptionalUserID()` where auth is optional (e.g. to vary visibility of results for anonymous vs. logged-in users).
  - **Issuing/clearing the cookie**: always go through `ITokenService` (`IssueAuthCookie(user)` / `DeleteAuthCookie()`); it owns the cookie name, cookie options and the 8h lifetime. Don't append/delete the cookie by hand. The token carries only the `id` and `ver` claims (HS256, validated with `ValidAlgorithms` pinned and a 30s `ClockSkew`). `Program.cs` refuses to start if `Jwt:Key` is missing or shorter than 32 bytes.
  - **Revocation (`TokenVersion`)**: `User.TokenVersion` is copied into the `ver` claim; `OnTokenValidated` in `Program.cs` compares it with the DB on every authenticated request and rejects mismatches (missing `ver` = 0). Incrementing `TokenVersion` logs the user out everywhere — this happens on password change (`PUT /api/User/me/password`, which then re-issues a cookie for the current browser), on a confirmed email change and on `POST /api/Auth/logout-all`. Any new "invalidate all sessions" feature should do the same.
  - **Two-factor authentication (email codes)**: when `User.IsTwoFactorEnabled`, `POST /api/Auth/login` (after a correct password only) issues no cookie; it emails a code and returns `{ twoFactorRequired, challengeToken }`. The challenge is a 10 min JWT from `ITokenService.CreateTwoFactorChallenge` with its own audience (`<Jwt:Audience>:2fa-challenge`), so the bearer handler never accepts it as a session, and it carries `ver`, so logout-all / password change kill pending logins. `POST /api/Auth/login/2fa` (challenge + code) issues the cookie, `login/2fa/resend` sends a new code. Enabling requires a verified email; enable/disable are two steps (password -> emailed code) in `SecurityController`. No recovery codes yet (TOTP and recovery codes are planned later).
  - **Security tokens**: `SecurityService` owns email verification, email change and 2FA codes, stored in `SecurityToken` as SHA-256 hashes only (`SecurityTokens` helper: generation, hashing, constant-time compare, lifetimes). Each `SecurityTokenType` is single purpose; issuing a token invalidates older unused ones of the same user + type; consuming is an atomic `ExecuteUpdate`; codes burn after 5 wrong tries; resends have a 60s cooldown. Link tokens (verify 24h, email change 1h) are confirmed by a POST from the frontend page, never by the GET of the link (mail scanners prefetch links).
  - **Email change** (`PUT /api/User/me/email`) needs the password and a verified email; it stores `User.PendingEmail`, mails a confirm link to the new address and a notice to the old one. Confirming sets the email, marks it verified and bumps `TokenVersion` (the browser that confirms keeps a fresh cookie if it's the same user). Existing users start unverified; unverified users aren't restricted except for 2FA and email change.
  - **Login** verifies unknown emails against a dummy BCrypt hash so response time doesn't reveal registered emails. Passwords are capped at 20 characters in DTOs and in `src/utils/validation.ts` — this keeps them under BCrypt's 72-byte limit even with multi-byte characters (C# and JS both count UTF-16 units, each at most 3 UTF-8 bytes), so no separate byte check is needed. Don't raise it above 24 without adding one.
  - **Usernames** are part of URLs, so `UsernameRules` allows 3–20 characters of `[A-Za-z0-9_-]` and reserves route words (`search`, `me`, ...), at registration and username change; mirrored by `usernameError` in `src/utils/validation.ts` and Android `Validation.usernameError`. The `RenameInvalidUsernames` migration renamed older offending accounts to `user_<id>` (with a system notification).
  - **Credentials in transit**: email/password are sent as plain JSON over HTTPS by design (visible in the browser's own DevTools, encrypted on the wire) — don't add client-side hashing/encryption. HSTS (`UseHsts`) is enabled outside Development.
- **Subscriptions (Premium)**: one monthly Premium plan (Stripe, test mode only). `UserSubscription` has one row per user who ever started a checkout (no row = Free, unique `UserID`, cascade with the user; `UpdatedAt` is a concurrency token so two parallel updates can't both notify); `SubscriptionEvent` stores received provider event IDs (dedupe/audit, never payloads). All decisions live in the pure, unit-tested `SubscriptionRules` (entitled while `Active` until the period end + 2 h renewal slack, `PastDue` for a 5 day grace from the first failed payment; `Apply` turns a provider snapshot into stored state; `DetectTransitions` finds Started / PaymentFailed / Cancelled / Ended). The local record only changes from what the provider reports: webhooks (`POST api/Subscription/webhook`, anonymous, signature-verified, not rate limited) are just triggers to fetch the current subscription (`IPaymentProvider.GetSubscriptionAsync`), so they are idempotent and order-independent, and notifications/emails come from local transitions only (`SubscriptionNotifier`, never throws). Providers: `StripePaymentProvider` (Stripe.net; the billing period is on the subscription item; a cancellation is either `cancel_at_period_end` (our cancel endpoint) or a `cancel_at` date (the customer portal), both read by `SubscriptionRules.StripeEndsAtPeriodEnd`) and the Development-only `FakePaymentProvider`, picked by `Subscription:Provider` in `SubscriptionSetup.AddSubscriptions`. `SubscriptionService` endpoints (`api/Subscription`): `plan` (anonymous), `status`, `checkout` / `portal` (return the provider page URL; `platform` web or android decides the return URL), `cancel` (= stop renewing, keep access to the period end) / `resume`, `sync` (asks the provider, used by the return pages), `return/android` (HTML page with the deep link), `dev/simulate`. Checkout, portal, cancel, resume and sync use the `billing` rate limit. `SubscriptionExpiryService` (hosted, every 15 min) re-checks lapsed running subscriptions with the provider and ends them if needed. Cancelling a subscription is not tied to account deletion (which doesn't exist yet) — add that step when deletion is built.
- **Entitlements**: `Entitlements.Catalog` (`Services/Entitlements.cs`) maps stable feature keys (`FeatureKeys`) to the minimum tier; coming-soon features are listed for the plans page but never granted. `IEntitlementService` reads the tier from the DB per request (never from the JWT, so changes apply on the next request). Lock an endpoint with `[Authorize]` + `[RequiresFeature(FeatureKeys.X)]`: users without access get **402** `{ error, code: "premium_required", feature }`, which both clients turn into the upsell. The auth user (`login`, `login/2fa`, `check-auth`) carries `tier`, `isPremium` and `entitlements`; `UserProfileDto.IsPremium` is the public badge. Granted features: `profile-badge`, `camera-recognition`, `offline-mode` (enforced on the Android device; the sync endpoints are deliberately not gated). Nothing is coming soon at the moment. A new Premium feature = a key + a catalog entry + `[RequiresFeature]` + the client upsell.
- **Camera recognition (Premium)**: spec in `_specs/camera-object-recognition.md`. `RecognitionController` (`api/Recognition`): `POST` (multipart, the photo in the `image` part; `[RequiresFeature(camera-recognition)]`, `recognition` rate limit), `GET {id}/items?offset=&count=` ("Show more", locked too, general limits), `GET allowance` (`[Authorize]` only: `{ enabled, premium, limit, remaining, resetsAt }`, so Free users can show the entry and the upsell). Errors are `{ error, code }`: 400 bad image, 413 too large, 409 `busy` (one recognition per user at a time, `RecognitionGate`), 429 `daily_limit` (with `resetsAt`), 503 `recognition_unavailable` / `source_unavailable`, 404 `not_found` (unknown, expired and someone else's id look the same). The code is in `Services/Recognition/`: `RecognitionService` runs cheap checks first (enabled, `ImageInspector` = JPEG/PNG by magic bytes and header dimensions, no decoding; gate; daily allowance), then the provider (`IRecognitionProvider`: `GeminiRecognitionProvider` = REST `generateContent`, key in the `x-goog-api-key` header, structured JSON output; on 429/5xx/timeout it moves to the next of `FallbackModels` at once and retries only the last model (exponential backoff with jitter), all attempts within `ProviderBudgetSeconds` (60 s, which plus the 15 s lookups stays below the Android client's 90 s); `FakeRecognitionProvider` in Development), then counts the recognition (`RecognitionUsage` row: the daily allowance is rows since UTC midnight, `RecognitionAllowance`; provider failures never count, an outage of TMDb / Spotify that leaves nothing to show refunds it), validates the answer (`RecognitionAnswerValidator`: clamps, caps, cleans; anything unusable is "nothing recognised"), resolves it (`MediaResolver`: exact title + year ±1 via `TitleMatcher`, or else a longer / shorter form of the title (`TitleContains`: "Star Wars: Episode IV - A New Hope" = TMDb's "Star Wars") among the top 3 search results with a known year ±1, the TMDb collection of the top direct movies, the best-known work of up to 2 actors/directors (most voted credits, not TMDb popularity, which is what is trending; credits under 2% of the person's top credit's votes dropped); at most 30 lookups, 4 in parallel, 15 s, stops after 3 failures in a row, successful lookups cached an hour in `IMemoryCache`; the strict `Find*` methods of `ITmdbService` / `ISpotifyService` throw `MediaSourceUnavailableException` instead of returning empty), ranks (`RecognitionRanking`: tier Direct > Universe > People > Similar, then confidence in 0.05 buckets, popularity, release date, title; dedupe keeps the closest tier; Similar only when the rest is thin; cap 60) and stores the list for paging (`RecognitionResultStore`, in memory, 30 min, bound to the user). The photo is read with `MultipartImageReader` straight into memory (never `IFormFile`, which spools to disk) and never stored or logged. The prompt and the answer schema live in `RecognitionPrompt` (the bake-off wording). Every number is in `RecognitionOptions` (`Recognition` section). The gate and the result store are in memory, so the API assumes a single instance.
- **Rate limiting**: configured in `Program.cs` (`AddRateLimiter`, `app.UseRateLimiter()` after auth so logged-in users are partitioned by `id`, anonymous ones by IP). A global limit (300/min) applies to every request, plus named policies applied with `[EnableRateLimiting("...")]`: `auth-attempt` (login/register/2FA login step, 10 per 10 min per IP), `credential-change` (change email/password, 2FA enable/disable steps, 5 per 10 min), `email-link` (anonymous verify-email / confirm-email-change, 10 per 10 min per IP, separate so opening links never uses up login attempts), `email-send` (resend verification / login code, 5 per 10 min), `external-api` (`MediaController`, 60/min — protects the TMDb/Spotify quotas), `billing` (subscription actions that call the payment provider, 15 per 10 min per user), `recognition` (camera recognition uploads, 5 per 10 min per user, on top of the daily allowance), `sync` (the Android offline sync, a token bucket per user: a burst of 20, then one every 6 s). Rejections are 429 with a JSON `{ error }` body and a `Retry-After` (the `sync` token bucket lease carries its own; sliding window leases carry none, so `RateLimitRetry` derives it: one segment of the longer window that applies; keep its `Windows` in sync with the policies). Counters are in-memory, so restarting the API resets them.
- **Media model (TPH inheritance)**: `Media` is an abstract EF Core entity with `Movie`, `Series`, and `Music` as concrete subtypes, mapped via table-per-hierarchy using the `MediaType` discriminator (configured in `AppDbContext.OnModelCreating`). Media rows are populated from external APIs — `TmdbService` (movies/series, via `ITmdbService`) and `SpotifyService` (music, via `ISpotifyService`) — and cached locally, keyed by `ExternalApiID` + `MediaType` (unique index; `ExternalApiID` is at most 64 characters). A row is only stored when the source knows the ID: `MediaService.ResolveAsync` / `LookupAsync` use the strict `Find*ByIdAsync` lookups (unknown = null, outage = `MediaSourceUnavailableException`) and return a `MediaLookupStatus`; `GetOrCreateMediaAsync` throws `MediaResolutionException`, which the global `MediaErrorFilter` turns into 404 `{ error, code: "media_not_found" }` or 503 `{ error, code: "source_unavailable" }` (review create, collection add); `GET api/Media/media/{type}/{id}` answers the same. Parallel first requests are caught as unique violations (`DbErrors.IsUniqueViolation`, also used for reviews, follows and collections). The daily cleanup deletes unused media rows left incomplete ("Unknown Title" / empty) by old failed lookups and fetches the used ones again. One review per user and media is a unique index too.
- **Database triggers**: Some invariants are enforced by SQL Server triggers created in migrations rather than in C#: `SetUpdatedAt` on `Review` (auto-updates timestamp) and `AddDefaultCollection` on `User` (creates a default collection on user insert). Keep this in mind when reasoning about `Review`/`Collection` state — it isn't always set from application code.
- **Collections**: `Collection` has a per-user unique `Name` constraint. The default `Favourites` collection (`Collection.DefaultName`, created by the trigger) is permanent: `CollectionService` rejects renaming, editing or deleting it, so its name always identifies it (no other collection can take the name). `CollectionDto.IsDefault` marks it for the frontend. `CollectionMedia` is a join entity with a composite key (`CollectionID`, `MediaID`) and cascade delete from both sides. `GET api/Collection/me/memberships` lists every `{ collectionID, mediaType, externalApiID }` in the caller's collections; the Android app caches it to show favourite/collection state on media cards (the web app doesn't use it yet).
- **Followers**: `UserFollower` is a self-referencing join entity on `User` with a composite key (`FollowerID`, `FollowingID`) and `Restrict` delete behavior (to avoid cascade cycles on `User` deletion).
- **Review replies**: `ReviewReply` (`ReviewReplyService` / `ReviewReplyController`, `api/ReviewReply`) threads are max 3 layers: review -> reply (`ParentReplyID` null) -> reply to reply. The layer is derived from the parent chain (no column); the service rejects replying to a reply that already has a parent. Replies have no visibility of their own — every read/write checks the parent review's visibility (hidden == 404), and private reviews can't be replied to. Deleting a reply is a soft delete (`IsDeleted`, content kept in the DB but never returned); a deleted reply is only listed as a placeholder while it has non-deleted children. Deleting a review cascades to all its replies in the DB (`ParentReply`/`User` FKs are `Restrict`). Listing uses keyset paging (`afterId`) for "load more"; review list responses include a non-deleted `ReplyCount`.
- **Account settings**: `AccountSettingsRoute` (`ui/settings/AccountSettingsScreen`, the web's `AccountSettingsMenu` and its dialogs on one screen) with Account (username, email, password), Security (verification state and resend, the pending email change with cancel, 2FA enable/disable) and Sessions (log out, log out of all devices). Everything goes through `AccountRepository` (`SecurityApi` + the `UserApi`/`AuthApi` account calls). `GET Security/status` is the only source of the email, `pendingEmail` and the 2FA state; the screen reloads it on every resume, and `AccountRepository.status()` also syncs the cached user's `isEmailConfirmed`. The dialog fields and rules (`UsernameForm`, `EmailForm`, `PasswordForm`, `TwoFactorFlow`: password step, then code step, resend re-requests with the kept password) are pure and unit-tested in `ui/settings/AccountForms.kt`. The API doesn't report its 60 s resend cooldown, so the app counts it down itself after a successful send. `logout-all` clears the session locally (`SessionManager.onLoggedOutEverywhere`), and a confirmed email change (on the web) revokes the app's session, which then logs out on its next request. The `credential-change` rate limit (5 per 10 min) is easy to hit while testing; restarting the API resets it.
- **Email verification**: the email links point to the web frontend and stay there (no Android link handling). `EmailVerificationBanner` (`VerificationBannerViewModel`) shows on Home and the owner's profile while the user is unverified, with "Resend email" and a dismiss that lasts until the app restarts (`AccountRepository.verificationBannerDismissed`, in memory). While it is shown, every resume calls `SessionManager.refreshUser()` (`check-auth`), so verifying in the browser hides it.
- **Achievements**: `Achievement` holds one row per tier (bronze/silver/gold); the tiers of one card share a `GroupCode` and a `Metric` (`AchievementMetric`, what is counted). `Categories` is a `[Flags]` enum (`AchievementCategories`), so one achievement can be in several categories. Definitions are seeded with `HasData` from `DAL/AchievementSeed.cs` — keep the IDs stable and add new tiers with new IDs plus a migration. `UserAchievement` (cascade deleted with the user) stores `CurrentProgress` and `IsUnlocked`; a missing row means zero progress.
  - **Evaluation**: `AchievementService.EvaluateAsync(userId, metrics...)` recounts the real totals and is called after `SaveChangesAsync` when content is created (and when a review is edited, as its score can change), not on deletes. Progress is the highest count ever reached (`Math.Max` with the stored value), so deleting content never lowers it, and deleting and recreating content doesn't raise it until the count beats the old peak. Unlocks are permanent. It never throws: failures are logged and swallowed, so the triggering action still succeeds. Counting rules live in `AchievementService.CountAsync` and are mirrored by the backfill SQL in the `AddAchievements` migration — reviews of every visibility count, replies exclude soft-deleted ones, low score is `Score <= 5.0`, and collections exclude the default `Favourites` (`Collection.DefaultName`). A new metric needs a case there and a hook where its data changes.
  - **Unlock delivery**: newly unlocked tiers go to every registered `IAchievementUnlockHandler`. `ResponseHeaderUnlockHandler` writes them (only for the requesting user) to the `X-Unlocked-Achievements` response header as JSON; the header is exposed in the CORS policy. `NotificationUnlockHandler` stores one notification per tier. Add a new handler instead of changing the service. `GET api/Achievement/{username}` is public.
- **Notifications**: `Notification` (recipient cascade, nullable actor `Restrict`) stores ready-to-display `Title`/`Message` plus a navigation target as plain ints/strings without FKs (`ReviewID`, `ReplyID`, `GroupCode`), so it outlives deleted content (the link then shows a not-found state). Types (`NotificationType`): `System`, `ReviewReply`, `ReplyReply`, `AchievementUnlocked`, `NewFollower`, `SubscriptionStarted`, `PaymentFailed`, `SubscriptionCancelled`, `SubscriptionEnded` (the last four route to the Premium page on both clients). Create them through `INotificationService` (`CreateAsync`, `CreateSystemAsync`, `NotifyNewFollowerAsync`) after the triggering `SaveChangesAsync`; like achievements, creation never throws. Hooks: `ReviewReplyService.CreateReplyAsync` (review author for layer 2, parent reply author for layer 3; never self, never a deleted parent, only if the recipient can still see the review), `FollowerService.FollowUserAsync` (deduplicated per actor for 7 days), the unlock handler, and `SecurityService`/`UserService` system messages. `NotificationController` (`api/Notification`, own notifications only — someone else's is a 404) lists with keyset paging (`status`, `sort`, `afterId`), has a cheap `unseen-count` for the badge polling, and mark seen/unseen, mark all seen, delete, delete all seen. Max 200 per user (oldest seen dropped first). A new type needs an enum value, a creation call where its data changes, and a route in `src/utils/notifications.ts`.
- **Single review / reply**: `GET api/Review/{id}` (with author, hidden == 404) and `GET api/ReviewReply/{id}` (the reply plus its layer-2 parent, deleted == 404) back the `/review/:reviewId?reply=` deep links.
- **Recent reviews**: `GET api/Review/recent?count=` (anonymous, 1–20, default 10) returns the newest public reviews that have some written text, with author and media; it feeds the Android home page (the web app doesn't use it).
- **Email**: `IAccountEmailService` builds the account emails (`EmailTemplates`: one inline-styled HTML layout + plain-text part, every value HTML-encoded) and only enqueues them on the singleton `EmailQueue` (bounded `Channel`); `EmailDispatcherService` (hosted) sends them with `SmtpEmailSender` (MailKit, `EmailOptions` from the `Email` section) with a couple of retries. Queued mail is lost on restart, which is fine because every email-dependent flow has a resend. Never log email bodies (they contain tokens/codes).
- **Background cleanup**: `DataCleanupService` (hosted, daily) deletes seen notifications older than 90 days, spent/expired `SecurityToken` rows, `RecognitionUsage` rows older than 7 days, `SyncOperation` / `SyncTombstone` rows older than `SyncRetention.Retention` (30 days), and repairs incomplete media rows.
- **Offline sync data model** (Android offline mode, spec `_specs/offline-mode-mobile-sync.md`): `Review` and `Collection` have a SQL Server `rowversion` (`RowVersion`, mapped to `long` with `RowVersionColumn` in `AppDbContext`) that changes on every write from any client. It is the base version an offline edit is checked against and the cursor of the changes feed. It is deliberately **not** a concurrency token, so the web keeps last-write-wins (don't switch it to `IsRowVersion()`). `Collection.UpdatedAt` is set by `CollectionService` on every change of the collection or its items (it has a DB default for the trigger-created Favourites), so item changes move the collection's rowversion. The delete paths of `ReviewService` / `CollectionService` add a `SyncTombstone` in the same `SaveChanges`. `SyncOperation` records each applied offline change by its device-generated `OperationID` (unique per user) and `ClientRef` (the device's temporary reference of what it created), so a change sent again is answered from `ResultJson` instead of being applied twice.
  - **Core writes**: the review, collection and follower services split each write into a public method (today's tuples and messages, used by the controllers) and a `*CoreAsync` / `SetFollowAsync` / `SetOrderAsync` method that takes stored media IDs, reports an exact status (`ReviewWriteResult`, `CollectionWriteResult`, `FollowWriteStatus` in `Services/WriteResults.cs`: e.g. `AlreadyPresent` vs `NotFound` vs `Locked`) and never evaluates achievements or sends the new-follower notification; the caller does that after committing. Change behaviour in the core method so the web and the sync stay the same. `MarkAllSeenAsync` / `DeleteSeenAsync` take an optional `upToId`.
  - **Push** (`POST api/Sync/push`, `SyncController`, `[Authorize]` but not Premium-gated so changes made offline still arrive after Premium lapses, `sync` rate limit, at most 50 ops / 512 KB): `{ userId, ops: [{ opId, type, clientRef?, dependsOn?, payload }] }`, `userId` must be the logged-in user (409 `user_mismatch`), 400 `too_many_ops` / `duplicate_op`. `SyncService` handles each op on its own (types and payloads in `Services/Sync/SyncOps.cs`, validated by `SyncOpParser`): a stored `OperationID` replays its result; a `dependsOn` op that wasn't applied (this request or stored) = `skipped`; `{ ref }` references resolve through the `ClientRef` of the applied create; media are resolved before the transaction (at most `MaxNewMediaLookups` = 20 new TMDb / Spotify lookups per request, the rest `retry deferred`; outage = `retry source_unavailable`, unknown = `rejected media_not_found`). Then one transaction: insert the `SyncOperation` first (a parallel push of the same op blocks on its unique key and then replays), lock the row (`UPDLOCK`), three-way merge against the device's `base` (`FieldMerge`: one side changed = that side, both differently = `conflict field_conflict` with `conflictFields`; `baseVersion` equal to the current rowversion = no merge needed), core write, store the result, commit; conflicts and rejections roll back (nothing stored, so the device can resend after the user decides). Achievements and the new-follower notification run after the commit; unlocks come back in the body (`unlocked`). Outcomes: `applied`, `merged`, `conflict` (`already_reviewed`, `deleted`, `modified_since` for deleting an edited review, `name_taken` with the existing collection, `collection_deleted`), `rejected` (`invalid`, `unknown_type`, `locked` = Favourites, `self`, `user_not_found`), `retry` (`busy` = deadlock / timeout, `server_error`), `skipped`. Already-done changes (adding a present item, removing a missing one, deleting a gone row, follow / unfollow) are `applied`. Profile and follows: the latest change wins, `previous` names overwritten profile values the device hadn't seen. Each result carries the server's version of the entity (`SyncReviewDto` / `SyncCollectionDto` with items / `SyncProfileDto`, built by `SyncStates`, UTC times, `version`). Review `createdAt` from the device is used within `ClientTimestamp` bounds (last 30 days, not in the future).
  - **Changes feed** (`GET api/Sync/changes?since=&syncedAt=&continued=&limit=`, `SyncChangesService`, `sync` rate limit): the user's own reviews and collections (every visibility, collections whole with their items) with `since <= RowVersion < MIN_ACTIVE_ROWVERSION()` plus the review / collection tombstones in that range, oldest first, at most `limit` (500) per page; rowversions are unique in the database, so `cursor` (last sent + 1, or the upper bound) is exact, and the upper bound means a write still in progress is never skipped. `fullResync` when `since` is 0 or `syncedAt` (the device's last finished sync) is older than the retention minus a day (tombstones may be gone): everything from 0, and the device drops what the full run didn't contain. `continued=true` marks a follow-up page (no full resync check, no account); the first page carries `account` (profile, following, followers, the newest 200 notifications via `NotificationService.GetLatestAsync`, unseen count). `POST api/Sync/visible { reviewIds, collectionIds }` (at most 1000 each) answers which of the other users' cached reviews / collections are still visible (own, public, or followers-only while following), so the device prunes the rest. Tests that read the feed call `AllWritesCommittedAsync()` first (`IntegrationTest`), because a transaction of a parallel test holds the upper bound back.
- **DTOs**: Request/response shapes live in `DTOs/`, kept separate from EF entities; controllers should not return entities directly.

### Android

Package `com.reviewapp.android` (`review-app-android/app/src/main/java/...`). MVVM with a manual DI container; it follows the web app's behavior and the `wireframes_mobile/` design.

- **DI**: `di/AppContainer.kt` (created in `ReviewApplication`) builds OkHttp, Retrofit, the APIs, repositories and `SessionManager` once. ViewModels get them through `viewModelFactory { initializer { appContainer()... } }` in their companion `Factory`; route arguments come from `createSavedStateHandle().toRoute<...>()`.
- **Layers**: `data/remote` (one Retrofit interface per controller in `Apis.kt`, `@Serializable` DTOs in `dto/Dtos.kt` with `toDomain()` mappers, note the API's `externalApiID` casing) → `data/repository` (`AuthRepository`, `MediaRepository`, `ReviewRepository`, `UserRepository`, `CollectionRepository`, `ReplyRepository`, `NotificationRepository`, `AchievementRepository`, `AccountRepository`, `SubscriptionRepository`) → `ui/<feature>` (Screen + ViewModel exposing `StateFlow` UI state and one-off events through a `Channel`). Domain models are in `domain/model`. New endpoints get a method in the matching `*Api` interface and repository, not direct calls from ViewModels.
- **Errors**: wrap calls in `apiCall { }` → `ApiResult` (`Success`/`Error(message, code)`). `ApiErrors.message` picks `{ error }`, then the first `ValidationProblemDetails` message, then a generic one per status code.
- **Session**: the same httpOnly JWT cookie as the web app. `data/local/SecureCookieJar` is the OkHttp `CookieJar`; it keeps `__Host-jwt_token` across restarts, encrypted with an Android Keystore AES-GCM key (`CryptoStore`) in the `session` DataStore (excluded from backups). Never read or log the token. `SessionManager` holds `AuthState` (`Loading`/`LoggedOut`/`LoggedIn(user)`), restores it on start with `GET Auth/check-auth`, and an OkHttp interceptor sends every 401 to `onUnauthorized()` (like `apiFetch` on the web), so revoked sessions log out on their next request. A second interceptor handles the other response side effects: an `X-Unlocked-Achievements` header goes to `AchievementRepository.onUnlockHeader`, and every successful non-GET request calls `NotificationRepository.onMutation()`. A password change re-issues the cookie in its response, and `saveFromResponse` replaces the stored one, so this device stays logged in while every other session is revoked.
- **Navigation**: type-safe Navigation Compose routes in `ui/navigation/Routes.kt`, wired in `AppNavHost.kt`. The bottom bar tabs (Home, Movies, Series, Music, Profile) each keep their own back stack. Login is pushed on top of the screen that needed it and pops back after success. The Profile tab (`MyProfileRoute`) and any user's page (`ProfileRoute(username, tab?)`, `tab` being a `ProfileTab` name to open on) share `ui/profile/ProfileScreen`/`ProfileViewModel`; without a route username it follows the logged-in user and shows a login prompt when logged out. Other profiles, follow lists, collections, user search, review pages, the notifications screen and the account settings are pushed onto the current tab's stack.
- **Lists**: infinite scroll with `ui/PagedLoader` (page-based endpoints, de-duplicates by key, retry, `remove` for local deletes) and `InfiniteListEffect`. Media cards load their average score lazily through `ReviewRepository.requestStats` (shared cache, at most 4 parallel requests). `MediaRepository` caches every media it returns, so the details screen opens without refetching. Review list filters (`ReviewsHeader`, `ReviewFilterChips`, `ScoreRangeSheet`) are shared in `ui/components/ReviewFilters.kt`.
- **Change events**: repositories emit `SharedFlow`s so other screens refresh without refetching everything: `ReviewRepository.changes` (review saved or deleted, deletions carry the review id; details, home and the owner's profile), `ReplyRepository.replyCountChanges` (review cards patch their reply count through `PagedLoader.update`), `UserRepository.followChanges` (profile header counts) and `CollectionRepository.changes` (profile collections tab, collection screen).
- **Review page and replies**: tapping any review card opens `ReviewRoute(reviewId, replyId?)` (`ui/review/ReviewScreen`, the web's `ReviewPage`): the review, its reply thread and a reply bar at the bottom ("Replying to X" for a layer-3 reply). - **Notifications**: `NotificationRepository` holds the unseen count (`unseenCount`, 0 while logged out; responses from an earlier session are dropped). It is refreshed on login, by `NotificationPollingEffect` in `ReviewAppRoot` (every 45 s while the app is at least STARTED, and at once when it comes back to the foreground; in-app only, no system notifications) and 800 ms after the user's own writes (`onMutation`, debounced). The activity-scoped `NotificationBadgeViewModel` feeds the Home top bar's `NotificationBell` (hidden when logged out) and a dot on the Home tab. `NotificationsRoute` (`ui/notifications/NotificationsScreen`, the web's `NotificationsDialog` full screen as in the wireframe) pages with the keyset cursor (20 per page, infinite scroll), has Seen / Unseen chips (exactly one on filters, both or neither = all) and a sort, and its actions are optimistic with rollback; the list rules are in the pure, unit-tested `NotificationListState`. "Take me there" goes through `notificationTarget` (same mapping as the web's `getNotificationRoute`): replies to `ReviewRoute(reviewId, replyId)`, new followers to their profile, unlocks to the user's own `ProfileRoute(me, Achievements)`. A new `NotificationType` needs an enum value (unknown names show as `System`) and a case there.
- **Achievements**: the profile's Achievements tab loads `GET Achievement/{username}` on first open and filters/sorts locally with `util/Achievements.kt` (mirrors `src/utils/achievements.ts`: overlapping statuses, OR within a group and AND across, stable "Unlocked first" sort; unit-tested). Each card is an `AchievementRow` (wireframe layout: icon and tier medals, next tier's goal and progress, greyscale while locked). The icons are vector drawables hand-converted from `review-app/public/achievements/*.svg` (`res/drawable/achievement_<key>.xml`, mapped in `achievementIcon`, trophy fallback), so a new or changed SVG must be converted too. Unlocks from the response header are queued by the activity-scoped `UnlockBannerViewModel` and shown one at a time by `UnlockBannerHost` (5 s, top of the screen, tap opens the Achievements tab); the owner's open tab reloads after an unlock.
- **Collections and favourites**: `CollectionRepository.mine` (`MyCollections`) caches the logged-in user's collections and memberships (`GET Collection/me/memberships`, keyed by media key), loaded on login and cleared on logout, so the heart is a real Favourites toggle and the add-to-collection sheet shows checkmarks. Membership changes are optimistic, serialized with a mutex, and reverted and reloaded on failure. `ui/collection/CollectionActions.kt` holds an activity-scoped `CollectionActionsViewModel` that `CollectionActionsHost` (around the nav host in `ReviewAppRoot`) provides through `LocalCollectionActions`; `MediaCollectionButtons` reads it, so any media card shows the buttons for logged-in users without extra parameters, and errors go to the root snackbar. The collection screen reorders with `sh.calvin.reorderable` (long-press drag in a `LazyVerticalGrid`): the list moves locally and one `PUT reorder` is sent on drop with the item's final index.
- **Premium**: `PremiumRoute` (`ui/subscription/PremiumScreen`, the web's `PremiumPage`: plans, subscribe, the subscription card with cancel/resume/payment details, a link to camera recognition) is opened from the account settings' Subscription section (the inline `PremiumUpsell` for Free users), notifications and the 402 upsell. Payment pages open in the browser (`LocalUriHandler`); the provider returns through the API's `return/android` page to `reviewapp://subscription/{result}` = `SubscriptionReturnRoute` (`SubscriptionReturnScreen`: waits for the session, `awaitPremium` = `sync` then polling). `MainActivity` is `singleTask`, and `ReviewAppRoot` sends deep links of new intents to `navController.navigate(uri)` (`handleDeepLink` would restart the task for the browser's NEW_TASK intents); cold starts use the graph's deep links. Test with `adb shell am start -d "reviewapp://subscription/success"`. A third OkHttp interceptor reports 402s to `SubscriptionRepository.onPremiumRequired()` (refreshes the user), and the activity-scoped `PremiumRequiredHost` shows the dialog. `AuthUser.isPremium` / `entitlements` / `hasFeature` come from check-auth; the repository refreshes the user after every subscription change. The card's rules (chips, date label, which actions) are the pure, unit-tested `subscriptionView` in `ui/subscription/SubscriptionUi.kt`. `PremiumBadge` shows next to the username on profiles with `isPremium`.
- **Camera recognition**: `RecognitionRoute` (`ui/recognition/RecognitionScreen`, the web's `RecognitionPage`), opened from the Home top bar's camera icon (logged-in users) and the Premium screen. `RecognitionViewModel` keeps the step (`RecognitionStep`: Start, Camera, Preview, Recognizing, Results) and the pure, unit-tested `RecognitionResults` (merge by media key, "Show more", end, failed, expired); the photo path and the recognition id + shown count are in the `SavedStateHandle`, so process death reloads the list with `items?offset=0&count=`. The camera is CameraX (`CameraCapture`: `LifecycleCameraController` + `PreviewView`, a front-only device uses the front camera); the permission is asked when "Take a photo" is tapped (rationale dialog, denied, "don't ask again" with an "Open settings" link, re-checked on resume); "Choose a photo" is the system photo picker (no storage permission). `RecognitionPhotos` (`data/local`) keeps photos only in `cacheDir/recognition` and prepares the upload (bounds-first decode with `inSampleSize`, EXIF rotation, at most 1280 px, JPEG 85; the math is the pure `util/ImageDownscale`) and deletes them once sent. `RecognitionApi` is a `@Multipart` Retrofit interface on its own OkHttp client (read 90 s, write 60 s, same cookie jar and interceptors). `ApiResult.Error.reason` carries the API's `code` (e.g. `daily_limit`, `not_found`). `MediaCard` has an optional `badge` (the tier label). The manifest declares `CAMERA` and `camera.any` as not required. On the emulator start it with `-camera-back virtualscene`, and push a test photo with `adb push x.jpg /sdcard/Pictures/` plus a media scan broadcast for the picker.
- **Offline mode (Premium, being built: spec `_specs/offline-mode-mobile-sync.md`)**: the foundations are in `data/sync/` and `data/local/offline/`.
  - **Connectivity**: `ConnectivityMonitor` combines Android's default network (`NET_CAPABILITY_VALIDATED`, so a captive portal is offline; `ACCESS_NETWORK_STATE`) with what the API requests tell: the outermost OkHttp interceptor reports any response / an `IOException` (not a cancelled call), and while the backend is unreachable on a working network a plain client probes `Subscription/plan` every 30 s. The pure `ConnectivityState` gives `Online` / `Offline` / `ServerUnreachable`. `ApiResult.Error.isNetwork` marks failures without an answer.
  - **Offline start**: `SessionCache` keeps the last confirmed user and when (`ClockReading`: wall clock, `elapsedRealtime`, boot count) encrypted in the `session` DataStore. `SessionRestore.decide` (pure) opens the cached user when the backend can't be reached, if they have `offline-mode`, the switch is on and the grace period runs (`OfflineAccess`, 7 days, measured so a clock set back can't extend it). `SessionManager.health` is then `Unverified` (cookie stored) or `NeedsLogin` (cookie expired); `AuthState` is unchanged. When the connection returns `ReviewApplication` calls `restoreIfNeeded()`: it verifies (`check-auth`), or logs out a `NeedsLogin` session so the user logs in again. A 401 clears the cookie and the cache (never reopened offline), never the offline database. `logout` / `logout-all` emit `explicitLogouts`.
  - **Gateway**: `OfflineGateway` decides `OfflineMode` per logged-in user with the pure `OfflineModeRules`: `Inactive` (Free, switched off, logged out: today's online-only path), `Preparing` (first download not finished, `sync_meta.prepared`), `Active`, `ReadOnly` (grace over: read only) and `Draining` (switched off or Premium ended with changes still waiting: they are still sent). It keeps the user's database open while the mode uses one (`database()` is null otherwise) and deletes the copy when it isn't wanted and nothing waits: switched off, a lapse confirmed by the backend (never one seen only in the device's cache), an explicit logout. `status` (mode, waiting changes, last sync, grace left) feeds the UI.
  - **Databases**: `DatabaseManager` keeps one encrypted file per user (`noBackupFilesDir/offline/offline_<userId>.db`, never backed up or transferred), at most one open. The key (`DatabaseKeyStore`) is random per user, wrapped by its own Keystore key (`review_app_db_key`) in the `session` DataStore; a lost key or an unreadable file starts a new empty copy. Tables (`OfflineEntities.kt`): own `reviews`, `collections`, `collection_items`, `media`, `profile`, `known_users`, `follows`, `notifications`, `achievements_json`, `snapshots`, `server_shadow`, `outbox`, `id_map`, `drafts`, `pending_unlocks`, `sync_meta`; ids are the backend's (negative = created offline), enums the API's ints, server times ISO strings.
  - **UI**: `ConnectivityStrip` (above the bottom bar in `ReviewAppRoot`, texts from the pure `connectivityBanner`), `OfflineSettingsRoute` (`ui/offline/OfflineSettingsScreen`, from the account settings: the switch (per account, on by default), the status card from the pure `offlineStatusView`, storage used, a confirmation before switching off; the upsell for Free users). `SettingsStore` also holds the cache budget and Wi-Fi-only download setting for the library download.
  - **Offline reading, network first**: every read still goes to the API; only a request that gets no answer (`ApiResult.Error.isNetwork`) falls back to the device, and the result then has `ApiResult.Success.cachedAt` (lists show "Updated ..."). Two sources:
    - *Snapshots* (everything the user has seen): `SnapshotInterceptor` (the outermost OkHttp interceptor, so the connectivity interceptor still sees the failure) stores each 200 answer of a GET in the open copy's `snapshots` table and serves it again when the request fails. `SnapshotPolicy` decides what is kept (never auth, security, subscription, recognition, sync, the live searches, nor what comes from the tables); `SnapshotIndex` records the other users' review / collection ids a snapshot shows. Each `apiCall` passes a `CallProbe` (a thread local read by Retrofit's `ProbingCallFactory`, tagged on the OkHttp request) that says whether a snapshot may answer it and reports the snapshot's age back.
    - *The synced tables* (the user's own content, complete): repositories call `LocalLibrary.networkFirst(own, ...)`: own content refuses snapshots and reads `LocalReads` (the pure `LocalReviewQuery` / `LocalCollectionQuery` / `LocalNotificationQuery` answer with the API's filters, sorts and pages). Own profile and follow lists prefer their snapshot (counts, join date) and fall back to the tables. Covered: own reviews (profile tab, review page, the review form's "your review"), collections (tab, collection page, the hearts and checkmarks of `MyCollections`), follow lists, notifications and the unseen count. Reply counts aren't in the feed: the online profile list stores them (`rememberReplyCounts`).
  - **Pull**: `SyncEngine` (single flight: a `Mutex` and a conflated trigger channel) runs on: a copy opening, back online, the user's own online writes (debounced), every 10 min, "Sync now", and the library download. It pages `GET Sync/changes` (500 per page) and applies each page in one Room transaction through the pure `ChangesApplier` (entities with a pending outbox change are never overwritten, only their `server_shadow`; one review per title: a review arriving for a title another local row holds replaces a stale row, while a row with waiting changes stays and the push reports the conflict); a full resync drops the rows the run didn't send and only stores its cursor at the end (an interrupted one starts over). Afterwards (every 30 min at most) `POST Sync/visible` prunes snapshots showing content its owner has hidden, unreferenced opened media beyond 2000 go, and snapshots are evicted to the budget (`SnapshotEviction`, least recently used first). `sync_meta.prepared` ends `Preparing`.
  - **Images**: `ReviewApplication` is Coil's `ImageLoaderFactory`: a disk cache of the budget's image share (`CacheBudget.imageBytes`, three quarters; snapshots get a quarter) that ignores cache headers. `OfflineImageStore` keeps small (TMDb `w185`) poster copies of the user's own content in `noBackupFilesDir/offline_images/<userId>` (deleted with the copy); `OfflineImageInterceptor` serves them while offline.
  - **Library download** (`LibraryDownloadWorker`, WorkManager, unique `library-download`, Wi-Fi only = `UNMETERED`): sync, then for every media of the own content the details page and average score (as snapshots, about one per second for the `external-api` limit) and the poster copy; resumable because kept ones are skipped. Progress and "Last done" are on the offline settings, with "Sync now", the cache size and "Clear cached data" (snapshots, opened media and Coil's caches; own content and the outbox stay).
  - **Without a connection**: lists end with an offline note instead of an error (`PagedList.offlineEnd`, a first page with nothing saved says so), the media search searches the offline library (`OfflineSearch`, with a notice), and `LocalIsOnline` (provided by `ReviewAppRoot`) lets online-only screens explain themselves: camera recognition, the Premium page, user search, the reply bar, the account settings (offline only Premium, offline mode and logout stay).
  - **Offline editing (the outbox)**: while the mode is `Active` every own write goes through `OfflineWriter`, online too (one path, exactly-once): the repositories check `offline.writer.canWrite()` and otherwise call the API as before. A write changes the copy and queues an op (`outbox`, payloads = the API's `SyncOps.cs` shapes in `dto/SyncDtos.kt`, JSON via `OpJson`) in one transaction, then asks the sync to run and schedules `SyncPushWorker`. Covered: reviews (create / edit / delete), collections (create / edit / delete, add / remove items incl. the hearts, reorder: the whole order), bio and picture, follow / unfollow / remove follower (the user's name comes along for the lists), notifications (seen, delete, mark all seen, delete seen, up to the newest on the device). The first local change of a thing keeps the backend's version as its `server_shadow` (pulls keep it current); updates carry the pre-edit values as `base` and the row's `version` as `baseVersion`. Creates get negative temporary ids (`sync_meta.next_temp_id`), `clientRef` = the create's opId (a UUID, unique across devices), and later ops point at them with `{ ref }` + `dependsOn`; `LocalLibrary.resolve` / `id_map` translate a temporary id once the backend gave the real one, so open screens keep working. The local name check refuses a taken collection name at once; online, `SyncEngine.awaitOp` waits up to 5 s for the answer so a review already written elsewhere or a name taken on the web is refused like before (the queued change is discarded).
  - **Pure outbox rules** (`OutboxRules.kt`, unit-tested): `OutboxCompactor` combines a new op with the still waiting ops of the same thing (key = entity type + id): edits fold into a waiting create or the first waiting edit (its base stays), create + delete = nothing sent, add + remove of a media cancel out, only the last reorder / follow state / seen state counts, profile edits merge field by field; ops being sent or in Sync issues are never touched. `SyncPlanner` picks the next batch (≤ 50) in queue order; an op in Sync issues or waiting for its retry blocks the later ops of the same thing, and an op waits for its `dependsOn` unless it is in the same batch. `RetryPolicy`: 5 s doubling to 1 h, ±20 % jitter, `Retry-After` as a minimum; `server_error` goes to Sync issues after 8 tries. `ResultInterpreter` maps `applied` / `merged` / `conflict` / `rejected` / `retry` / `skipped` to outcomes; `rebase` moves the `baseVersion` of waiting edits after an unmerged apply.
  - **Push**: `PushRunner` (in front of every pull, `SyncEngine.runOnce`) marks the batch in flight, sends it, and applies each answer in one transaction: done = out of the queue (a create's temporary id is remapped in its row, the waiting ops and `id_map`), the backend's entity replaces the row when nothing else waits for it (else it becomes the shadow), markers cleared; conflict / rejection = `CONFLICT` / `REJECTED` with the answer kept, marker `ISSUE`; retry = backoff. A request without an answer leaves everything waiting (`Offline`), 401 = `NeedsLogin` (nothing lost), 429 = `Paused` until `Retry-After` (`SyncEngine.pausedUntil`, the strip says so), other failures back off per op. Ops in flight when the app died go back to waiting on the next run (`recover`); the backend recognises them by opId. `SyncEngine` wakes itself for the next retry time. Unlocks come in the push answer (the unlock-header interceptor skips `/Sync/`): banners in the foreground, `pending_unlocks` otherwise, shown on the next app open (`AppContainer.showPendingUnlocks`, the app's foreground is tracked in `ReviewApplication`, which also syncs on every open). After a push `ReviewRepository.onSynced` / `CollectionRepository.onSynced` reload the lists (`fromSync` events don't trigger another sync).
  - **Background**: `SyncPushWorker` (WorkManager, unique `sync-push`, `KEEP`, needs a network, exponential backoff) is scheduled with every queued change; it only pushes for the stored user (`SyncEngine.pushOnly`), retries while something is left to send, and gives up quietly on a 401.
  - **Reads while changes wait**: `LocalLibrary.networkFirst(pendingTypes = ...)` answers from the copy without a request while ops of those entity types wait (the copy is what the user did); the own profile header gets the waiting bio, picture and counts overlaid. Domain models carry `syncState`; `SyncBadge` shows "Waiting to sync" / "Needs attention" on profile review cards, collection cards and the collection screen (and its items), and notification cards.
  - **UI**: the strip says "Syncing N changes…", "Sync paused…", "N changes waiting to sync" or "N changes need your attention" and opens `PendingChangesRoute` (`ui/offline/PendingChangesScreen`: each op in plain language from the pure `OutboxDescriber`, its state, Discard with confirmation; also from the offline settings). `OfflineWriter.discard` throws away the waiting ops of that thing and restores its shadow (something created offline disappears), not while one is in flight. The review form keeps its unsaved text in `drafts` (debounced) and offers it back after the app was killed; leaving the form deliberately or saving drops it.
  - **Sync issues** (conflicts and rejections, `ConflictRoute(seq)` = `ui/offline/ConflictScreen`, opened from the "Needs your attention" section of the waiting changes screen): the pure `IssueRules` (`data/sync/IssueRules.kt`) classify an issue (`IssueKind`: field conflict, deleted elsewhere, edited since, already reviewed, name taken, rejected), list the conflicting fields (`FieldDiff`) and turn the user's choices into the fields to send (`resolveReview` / `resolveCollection`: a conflicting field as chosen, a field only I changed mine, any other theirs); the pure `issueView` (`ui/offline/IssueView.kt`) picks the texts and the offered `IssueAction`s. `ConflictResolver` applies a decision in one transaction and asks the sync to run: field choices (per field keep mine / use theirs / edit a combination prefilled with both texts) requeue the change on top of the backend's version (`baseVersion` = its version, so it applies as is) and fold my later edits of the same thing into it; recreate (deleted elsewhere) gives the local row a new temporary id and queues a create (a collection with an add for each item it shows); delete anyway sends the delete with the edited version; keep mine (already reviewed) turns my review into an edit of the backend's one (its id from then on, through `id_map`); rename or merge into the existing collection (a name taken by a collection made here: its items move there, the waiting adds / removes are retargeted with `IssueRules.retarget`); try again (a server that kept failing); use theirs = `OfflineWriter.discard` plus the backend's version from the answer. Nothing is thrown away before the user picks; an issue blocks only the later changes of the same thing.
  - **Sync summary and unlocks**: `PushRunner` collects the unlocks of a whole run and delivers them once (`AchievementRepository.unlocks` emits groups; `UnlockBannerHost` shows a group as one banner, "3 achievements unlocked!"), and `PushOutcome.Done` counts the changes that had waited (older than 15 s when answered, i.e. made offline), the issues among them and the profile fields whose value from elsewhere mine replaced (`previous`). `SyncEngine.summaries` feeds `SyncSummaryHost` on the root snackbar ("Synced 7 changes. You unlocked 1 achievement.", with "Review" when something needs the user, pure `syncSummaryMessage`); changes made online are synced at once and get no summary.
  - **Accounts**: logging out with changes waiting opens "Changes not synced" (sync first, when online: logs out once nothing is left; log out and discard: `OfflineGateway.discardOnLogout` deletes the copy; cancel); `logout-all` keeps them and says so. Another user's copy with unsent changes (their session ended without a logout) is never opened as the current one; `DatabaseManager.othersWithChanges` counts them and the offline settings show a neutral "Changes from another account" row with Discard. The offline settings show the status and the waiting changes also when Premium ended (Draining), so issues stay reachable.
  - **Tests**: the pure rules are JVM tests (`OutboxRulesTest`, `OutboxDescriberTest`, `IssueRulesTest`, `SyncIssuesTextsTest`, `ChangesApplierTest`, ...); `PushScenariosTest` (`androidTest`, real encrypted database + a scripted fake `SyncApi`) covers a lost answer, a drop between batches, 401, 429, a conflict in a dependent chain, the app killed mid-send, temporary id remapping and Discard; `ConflictScenariosTest` takes every Sync issues decision from the conflict to the change applied.
- **Theme**: fixed MUI-like palette (no dynamic color) in `ui/theme`, plus `AppTheme.extendedColors` (success/warning, pros/cons boxes) and `ScoreTier.color()`. Score thresholds, validation limits and filter values live in `util/` and mirror the web app (`Format.kt`, `Validation.kt`, `DiscoverOptions.kt`). The theme mode (system/light/dark) is stored by `SettingsStore`.
